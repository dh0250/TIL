# StudyOn 테스트 DB 분리와 락 없는 동시성 테스트 구현

StudyOn 예약 기능의 동시성 문제를 재현하기 위해 개발 DB와 분리된 테스트 DB를 구성하고, 실제 PostgreSQL에서 락 없이 같은 시간대 예약이 중복 저장되는 통합 테스트를 작성했다. 단위 테스트의 mock 방식으로는 DB 락과 트랜잭션 경쟁을 검증할 수 없으므로 Spring Boot 통합 테스트, 별도 트랜잭션과 여러 스레드를 사용하도록 정리했다.

---

# 1. 개발 DB와 테스트 DB 분리

개발 중 사용하는 `studyon` DB에서 테스트를 실행하면 예약 데이터가 섞이거나 삭제될 수 있다. 따라서 같은 로컬 PostgreSQL 서버 안에 `studyon_test` DB를 별도로 만들었다.

```text
PostgreSQL 서버
├── postgres      : DB 생성·역할 관리용 관리자
├── studyon_user  : StudyOn 애플리케이션 전용 역할
│
├── studyon       : 로컬 개발 DB
└── studyon_test  : 자동화·동시성 테스트 전용 DB
```

`studyon_user`는 `studyon` DB의 소유자이며, 애플리케이션이 실제로 사용하는 계정이다. 테스트 DB도 같은 계정을 소유자로 만들고, DB 생성 권한만 추가했다.

```sql
ALTER ROLE studyon_user WITH LOGIN CREATEDB;

CREATE DATABASE studyon_test
OWNER studyon_user;
```

`SUPERUSER` 권한은 애플리케이션 계정에 줄 필요가 없다. 개발·테스트 DB 생성이 필요한 범위까지만 `CREATEDB` 권한을 부여하는 편이 안전하다.

# 2. Spring Profile과 application-test.yml

Spring Boot는 기본 설정 파일을 읽은 뒤 활성화된 프로필 이름에 맞는 설정 파일을 추가로 읽는다.

```text
application.yml
+ application-test.yml
= 테스트 실행 최종 설정
```

테스트 클래스에 아래 애노테이션을 붙이면 `test` 프로필이 활성화되고, Spring Boot가 `application-test.yml`을 자동으로 읽는다.

```java
@SpringBootTest
@ActiveProfiles("test")
class ConcurrencyNoLockTest {
}
```

테스트 환경에서는 DB 주소와 JPA 검증 설정만 개발 설정과 다르게 둔다.

```yml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/studyon_test

  jpa:
    hibernate:
      ddl-auto: validate
```

같은 설정 키가 `application.yml`과 `application-test.yml`에 모두 있으면 테스트 프로필 값이 우선한다. 반대로 테스트 파일에 없는 `username`, `password`, CORS 등 공통 설정은 `application.yml`과 `.env`의 값을 그대로 사용한다.

이미 테스트 DB에 `schema.sql`과 `study_rooms_data.sql`을 직접 실행했으므로, 테스트에서는 테이블을 새로 만들거나 지우는 `create-drop` 대신 엔티티와 테이블 구조만 확인하는 `validate`를 사용한다.

# 3. 단위 테스트와 동시성 통합 테스트의 차이

기존 `ReservationServiceTest`는 Mockito로 Repository를 mock 처리하는 단위 테스트다. `given(...).willReturn(...)`으로 DB가 반환할 값을 흉내 낼 수 있지만, 실제 PostgreSQL의 락·트랜잭션·동시 INSERT는 발생하지 않는다.

동시성 테스트는 실제 DB에 연결해야 하므로 다음과 같이 작성한다.

```text
@SpringBootTest
→ Spring Context와 실제 Repository 사용

@ActiveProfiles("test")
→ studyon_test DB 연결

ExecutorService
→ 예약 요청을 여러 스레드에서 동시에 실행

TransactionTemplate
→ 각 작업 스레드의 DB 작업을 별도 트랜잭션으로 실행
```

테스트 전후에는 예약 데이터만 비운다.

```java
@BeforeEach
void setUp() {
    reservationRepository.deleteAllInBatch();
}

@AfterEach
void tearDown() {
    reservationRepository.deleteAllInBatch();
}
```

`deleteAllInBatch()`는 엔티티를 하나씩 조회하지 않고 `DELETE FROM reservations`에 해당하는 일괄 삭제 SQL을 실행한다. 테스트 DB에서만 사용해야 하며, 개발 DB에서 실행하면 모든 예약 행이 삭제된다.

# 4. 락 없는 예약 중복 재현

현재 실제 예약 서비스는 `findForUpdateByIdAndActiveTrue()`로 스터디룸 행에 비관적 쓰기 락을 획득한다. 락이 없을 때의 문제를 재현하려면 기존 서비스를 수정하지 않고, 테스트 클래스 내부에서 일반 조회 메서드 `findByIdAndActiveTrue()`를 사용하는 테스트 전용 예약 생성 로직을 작성했다.

```text
요청 A: 일반 조회 → 중복 예약 없음 확인
요청 B: 일반 조회 → 중복 예약 없음 확인
요청 A: 예약 저장
요청 B: 예약 저장
```

두 요청은 서로 다른 비회원 정보지만 같은 스터디룸과 같은 시간대를 요청한다.

```text
같은 값
- studyRoomId
- startAt
- endAt

다른 값
- 이름
- 이메일
- 전화번호
- 이용 목적
```

이렇게 하면 실제로는 서로 다른 사용자가 동시에 같은 방을 예약하는 상황을 재현할 수 있다.

# 5. ExecutorService와 CountDownLatch

`ExecutorService`는 여러 작업을 실행할 스레드 풀이다. `newFixedThreadPool(2)`로 예약 요청을 처리할 스레드 두 개를 준비했다.

```java
ExecutorService executorService = Executors.newFixedThreadPool(2);
```

두 요청을 단순히 제출하면 실행 순서에 따라 한 요청이 먼저 저장되고, 다른 요청이 중복을 발견할 수 있다. 중복 저장을 안정적으로 재현하기 위해 `CountDownLatch` 두 개를 사용했다.

```java
CountDownLatch checkedLatch = new CountDownLatch(2);
CountDownLatch allowSaveLatch = new CountDownLatch(1);
```

각 latch의 역할은 다르다.

```text
checkedLatch
→ 작업 스레드 2개가 모두 중복 검사를 끝냈는지 메인 스레드에 알림

allowSaveLatch
→ 메인 스레드가 두 작업 스레드에게 저장을 허용하는 출발 신호
```

흐름은 다음과 같다.

```text
작업 스레드 A: 중복 검사 → checkedLatch.countDown() → allowSaveLatch.await()
작업 스레드 B: 중복 검사 → checkedLatch.countDown() → allowSaveLatch.await()

메인 스레드: checkedLatch가 0이 될 때까지 최대 5초 대기
→ allowSaveLatch.countDown()
→ A와 B가 거의 동시에 예약 저장
```

`await()`는 latch 카운트가 0이 될 때까지 현재 스레드를 대기시킨다. 인자 없이 호출하면 시간 제한 없이 기다리고, `await(5, TimeUnit.SECONDS)`처럼 호출하면 최대 5초만 기다린 뒤 성공 여부를 boolean으로 반환한다.

# 6. Future와 동시 작업 예외 확인

`submit()`은 작업 결과와 상태를 담는 `Future`를 반환한다.

```java
Future<?> firstFuture = executorService.submit(...);
Future<?> secondFuture = executorService.submit(...);
```

`Future.get()`은 작업 완료까지 기다리고, 작업 스레드에서 발생한 예외도 메인 테스트 스레드로 전달한다.

```java
firstFuture.get();
secondFuture.get();
```

두 작업이 모두 성공한 뒤 예약 테이블의 행 수가 2개인지 확인한다.

```java
assertThat(reservationRepository.count()).isEqualTo(2);
```

테스트 시작 전에 예약 테이블을 비웠고, 두 요청이 같은 스터디룸·같은 시간대를 사용하므로 이 검증은 락이 없을 때 중복 예약이 두 건 저장됐다는 것을 뜻한다.

---

# 7. 정리

- `studyon_test` DB를 분리해 개발 DB 데이터가 동시성 테스트에 영향을 받지 않도록 구성했다.
- `@ActiveProfiles("test")`로 `application-test.yml`을 읽고 테스트 DB URL만 덮어쓴다.
- 동시성 검증은 mock 기반 단위 테스트가 아니라 실제 PostgreSQL을 사용하는 통합 테스트로 진행한다.
- `ExecutorService`는 두 예약 요청을 별도 스레드에서 실행한다.
- `checkedLatch`는 두 요청의 중복 검사 완료를 확인하고, `allowSaveLatch`는 저장을 동시에 시작시키는 역할을 한다.
- `Future.get()`으로 작업 스레드의 성공·예외를 메인 테스트에서 확인한다.
- 락 없는 테스트가 완료되면 같은 조건으로 비관적 락, Redis 분산 락 테스트를 추가해 결과와 경합 특성을 비교한다.

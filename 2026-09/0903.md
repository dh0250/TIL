# StudyOn API 통합 테스트 구조와 테스트 DB 선택 정리

예약 기능의 서비스 단위 테스트와 동시성 테스트에 이어, Controller부터 실제 DB까지 연결되는 API 통합 테스트를 추가하기 위한 구조를 정리했다. 기존 `studyon_test` DB를 재사용하는 방법과 H2 메모리 DB를 사용하는 방법을 비교했고, PostgreSQL 전용 기능을 검증해야 하는 현재 프로젝트에서는 실제 PostgreSQL 기반 테스트가 더 적합하다는 결론을 내렸다.

---

# 1. 테스트 종류별 역할과 패키지 구조

테스트는 검증 범위에 따라 단위 테스트, API 통합 테스트, 동시성 통합 테스트로 나눈다.

```text
src/test/java/com/studyon/studyon
├── service/
│   ├── StudyRoomServiceTest.java
│   └── ReservationServiceTest.java
├── integration/
│   ├── StudyRoomApiIntegrationTest.java
│   └── ReservationApiIntegrationTest.java
└── concurrency/
    ├── ConcurrencyNoLockTest.java
    └── ConcurrencyPessimisticLockTest.java
```

`service` 패키지의 테스트는 Mockito를 사용해 Repository를 mock 처리하는 단위 테스트다. 별도의 `unit` 패키지를 한 단계 더 만들지 않아도, 서비스 테스트라는 이름만으로 단위 테스트의 범위를 충분히 알 수 있다.

```text
service
→ Service 로직만 검증하는 단위 테스트

integration
→ Controller → Service → Repository → PostgreSQL 흐름 검증

concurrency
→ 여러 스레드와 실제 PostgreSQL 락·트랜잭션 검증
```

API 통합 테스트 작업을 위해 `dev` 브랜치에서 아래 브랜치를 생성했다.

```text
feature/api-integration-test
```

# 2. MockMvc 기반 API 통합 테스트

`MockMvc`는 실제 서버 포트 `8080`을 열지 않고도 HTTP 요청처럼 Controller를 호출할 수 있게 해주는 Spring 테스트 도구다.

```java
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
class ReservationApiIntegrationTest {
}
```

각 애노테이션의 역할은 다음과 같다.

```text
@SpringBootTest
→ Spring Context 전체를 띄운다.
→ Controller, Service, Repository를 모두 실제 Bean으로 사용한다.

@AutoConfigureMockMvc
→ MockMvc를 주입받아 HTTP 요청과 응답을 검증할 수 있게 한다.

@ActiveProfiles("test")
→ application.yml에 application-test.yml을 합쳐 테스트 DB 설정을 사용한다.
```

예약 생성 API 테스트에서는 요청 DTO를 JSON으로 변환해 `POST /api/v1/reservations` 요청을 보낸다.

```java
mockMvc.perform(post("/api/v1/reservations")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
        .andExpect(status().isCreated())
        .andExpect(jsonPath("$.studyRoomId").value(studyRoom.getId()))
        .andExpect(jsonPath("$.guestEmail").value("api-test@example.com"))
        .andExpect(jsonPath("$.status").value("CONFIRMED"));
```

`ObjectMapper`는 Java의 `ReservationCreateRequest` 객체를 JSON 문자열로 바꾼다. `jsonPath("$.status")`는 응답 JSON의 `status` 필드를 뜻하며, 예약 생성 결과가 `CONFIRMED`인지 확인한다.

```text
POST /api/v1/reservations
→ Controller가 JSON 요청을 DTO로 변환
→ Service가 검증·저장
→ Repository가 PostgreSQL에 INSERT
→ 201 Created와 응답 JSON 반환
```

# 3. API 통합 테스트 우선 검증 항목

처음에는 각 API의 성공 흐름을 하나씩 검증하고, 이후 예외 응답을 추가한다.

```text
StudyRoomApiIntegrationTest
- 운영 중인 스터디룸 목록 조회: 200 OK
- 날짜별 예약 가능 시간 조회: 200 OK

ReservationApiIntegrationTest
- 예약 생성: 201 Created
- 이메일·전화번호 예약 조회: 200 OK
- 예약 취소: 200 OK
```

성공 흐름이 통과한 뒤에는 아래 실패 흐름을 검증한다.

```text
- 존재하지 않는 스터디룸 예약: 404 Not Found
- 이미 예약된 시간대 예약: 409 Conflict
- 이메일·전화번호 형식 오류: 400 Bad Request
- 취소 마감 시각 이후 취소: 400 Bad Request
```

# 4. 테스트 데이터 정리 방식

현재 동시성 테스트는 `studyon_test` DB를 사용하고, 테스트 전후에 예약 전체를 비운다.

```java
@BeforeEach
void setUp() {
    reservationRepository.deleteAllInBatch();
}

@AfterEach
void tearDown() {
    reservationRepository.deleteAllInBatch();
}
```

별도 테스트 DB를 사용하면 개발 예약 데이터와 섞이지 않아 가장 안전하다. 반대로 작은 개인 프로젝트에서 로컬 개발 DB를 함께 쓰고 싶다면, 테스트 이메일 접두어를 고정하고 해당 데이터만 삭제하는 방법도 있다.

```java
@Transactional
long deleteByGuestEmailStartingWith(String guestEmailPrefix);
```

```java
private static final String TEST_EMAIL_PREFIX = "api-integration-test-";

@BeforeEach
@AfterEach
void cleanUp() {
    reservationRepository.deleteByGuestEmailStartingWith(TEST_EMAIL_PREFIX);
}
```

이 방식을 사용할 경우 모든 테스트 예약 이메일은 `api-integration-test-`로 시작해야 한다. 실제 운영 DB에서는 테스트를 실행하지 않는 것이 원칙이며, 삭제 범위를 분리하더라도 운영 DB 사용은 피해야 한다.

테스트가 예약을 저장하면 PostgreSQL의 auto increment 시퀀스도 증가한다. 테스트 행을 삭제하거나 트랜잭션을 롤백해도 ID 번호는 보통 되돌아가지 않는다.

```text
테스트 예약 생성 → id 15
테스트 예약 삭제
다음 실제 예약 생성 → id 16
```

ID는 연속 번호가 아니라 고유 식별자이므로 중간 번호가 비는 것은 정상이다.

# 5. H2 메모리 DB와 PostgreSQL 선택

H2는 테스트 실행 중에만 메모리에 생성되고, 테스트가 끝나면 자동으로 사라지는 경량 DB다.

```text
테스트 시작 → H2 메모리 DB 생성 → JPA 테이블 생성
테스트 종료 → H2 DB 삭제
```

H2를 사용하려면 테스트 의존성과 `application-test.yml`을 H2 설정으로 바꾸고 `ddl-auto: create-drop`을 사용한다.

```gradle
testRuntimeOnly 'com.h2database:h2'
```

```yml
spring:
  datasource:
    url: jdbc:h2:mem:studyon-test;MODE=PostgreSQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
    username: sa
    password:

  jpa:
    hibernate:
      ddl-auto: create-drop
```

하지만 StudyOn은 PostgreSQL의 `EXCLUDE USING gist` 배타 제약조건과 `PESSIMISTIC_WRITE` 비관적 락을 사용한다. H2는 이 PostgreSQL 전용 동작을 동일하게 지원하지 않으므로, H2에서 통과해도 실제 PostgreSQL의 중복 예약 방지와 동시성 동작을 보장할 수 없다.

```text
H2
→ 단순 Controller·Service·JPA 흐름 검증에는 사용 가능

PostgreSQL
→ 비관적 락, 배타 제약조건, 동시성 테스트에는 반드시 필요
```

현재 프로젝트에서는 DB를 두 종류로 관리하는 것보다 기존 `studyon_test` PostgreSQL DB 하나를 API·동시성 통합 테스트에 계속 사용하는 편이 실제 환경과 같고 단순하다.

# 6. 정리

- 단위 테스트는 기존 `service` 패키지에 두고, 별도 `unit` 패키지는 만들지 않는다.
- API 통합 테스트는 `integration` 패키지에 두고 `MockMvc`로 HTTP 요청·응답을 검증한다.
- `@SpringBootTest`는 전체 애플리케이션 계층을, `@AutoConfigureMockMvc`는 HTTP 요청 시뮬레이션을 제공한다.
- 테스트 DB를 유지하면 전체 예약 삭제를 안전하게 사용할 수 있다.
- 로컬 개발 DB를 재사용하려면 테스트 이메일 접두어로 삭제 범위를 제한할 수 있지만, 운영 DB에서는 실행하지 않는다.
- H2는 가볍지만 PostgreSQL 전용 락·배타 제약조건을 검증할 수 없어 현재 동시성 테스트의 대체 수단으로는 적합하지 않다.

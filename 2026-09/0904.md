# StudyOn 낙관적 락 예약 동시성 테스트 정리

비관적 락 구현과 비교하기 위해, 스터디룸의 `version` 컬럼을 이용하는 낙관적 락 예약 방식을 추가했다. 낙관적 락은 DB 행을 먼저 잠그지 않고 각 요청이 작업한 뒤, 커밋 시점에 버전이 바뀌었는지 확인해 충돌한 요청을 실패 처리하는 방식이다.

---

# 1. `@Version`과 낙관적 락

`study_rooms` 테이블에 버전을 저장할 컬럼을 추가했다.

```sql
ALTER TABLE study_rooms
    ADD COLUMN IF NOT EXISTS version BIGINT NOT NULL DEFAULT 0;
```

`StudyRoom` 엔티티에서는 `@Version` 필드로 연결한다.

```java
@Version
@Column(nullable = false)
private Long version;
```

JPA는 엔티티를 수정할 때 기존 버전을 조건으로 포함하는 UPDATE를 실행한다.

```text
요청 A, B가 version = 0인 스터디룸을 조회

요청 A 커밋
→ version 0 → 1 변경 성공

요청 B 커밋
→ version 0인 행을 변경하려 하지만 이미 1
→ 수정 행 수 0건 → 낙관적 락 충돌
```

일반 스터디룸 조회나 예약 가능 시간 조회는 버전을 올리지 않는다. 예약 생성에서만 강제 버전 증가 락을 사용한다.

---

# 2. Repository의 `OPTIMISTIC_FORCE_INCREMENT`

예약 생성 시 스터디룸의 일반 필드를 수정하지 않으므로, 단순 `OPTIMISTIC` 락만으로는 버전 증가가 보장되지 않는다. 따라서 `OPTIMISTIC_FORCE_INCREMENT`를 사용한다.

```java
@Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)
Optional<StudyRoom> findForOptimisticLockByIdAndActiveTrue(Long id);
```

이 락은 예약 생성 트랜잭션이 성공적으로 커밋될 때 스터디룸 버전을 증가시킨다. 별도로 `studyRoomRepository.save(studyRoom)`를 호출할 필요는 없다.

```text
예약 생성 요청
→ 스터디룸을 낙관적 락 모드로 조회
→ 중복 시간 검사
→ Reservation 저장
→ 커밋 시 StudyRoom version 증가 및 충돌 검사
```

예약 시간 중복으로 `ReservationConflictException`이 발생하면 트랜잭션 전체가 롤백되므로, 버전도 증가하지 않는다.

---

# 3. 예약 생성 서비스 변경

기존 비관적 락 조회 메서드 대신 낙관적 락 조회 메서드를 사용하도록 변경했다.

```java
StudyRoom studyRoom = studyRoomRepository
        .findForOptimisticLockByIdAndActiveTrue(request.studyRoomId())
        .orElseThrow(StudyRoomNotFoundException::new);
```

`Reservation`은 기존처럼 저장하고, 저장된 엔티티로 응답 DTO를 생성한다.

```java
Reservation savedReservation = reservationRepository.save(reservation);
return ReservationCreateResponse.from(savedReservation);
```

낙관적 락은 스터디룸을 저장하는 기능이 아니라, 예약 생성 요청끼리 같은 버전을 기준으로 충돌을 감지하는 기능이다.

---

# 4. 낙관적 락 동시성 테스트

`ConcurrencyOptimisticLockTest`는 실제 `ReservationService`를 호출해 낙관적 락이 적용된 전체 트랜잭션을 테스트한다.

```text
조건
→ 같은 스터디룸, 같은 10:00 ~ 11:00 시간대
→ 서로 다른 예약자 정보의 요청 2개

기대 결과
→ 예약 성공 1건
→ 낙관적 락 충돌 1건
→ DB 예약 행 1건
```

`ExecutorService`로 두 작업 스레드를 만들고, `CountDownLatch`로 두 스레드가 준비된 뒤 같은 시점에 예약 생성을 시작하게 한다.

```java
CountDownLatch readyLatch = new CountDownLatch(2);
CountDownLatch startLatch = new CountDownLatch(1);
```

```java
Future<?> firstFuture = executorService.submit(() -> {
    readyLatch.countDown();
    await(startLatch);
    reservationService.createReservation(firstRequest);
});
```

두 요청의 결과는 `Future.get()`으로 확인한다. 작업 스레드에서 발생한 예외는 `ExecutionException`으로 감싸져 전달되므로 `getCause()`로 실제 예외를 확인한다.

```java
try {
    future.get();
    successCount++;
} catch (ExecutionException e) {
    assertThat(e.getCause())
            .isInstanceOf(ObjectOptimisticLockingFailureException.class);
    conflictCount++;
}
```

마지막으로 성공·충돌 건수와 실제 저장 행 수를 함께 검증한다.

```java
assertThat(successCount).isEqualTo(1);
assertThat(conflictCount).isEqualTo(1);
assertThat(reservationRepository.count()).isEqualTo(1);
```

# 5. 예외 응답 처리

낙관적 락 충돌은 Spring의 `ObjectOptimisticLockingFailureException`으로 전달된다. API에서는 사용자가 다시 시도할 수 있도록 409 Conflict로 변환한다.

```java
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<ProblemDetail> handleOptimisticLock(
        ObjectOptimisticLockingFailureException exception
) {
    return createProblem(
            HttpStatus.CONFLICT,
            "다른 요청이 먼저 예약했습니다. 다시 시도해주세요."
    );
}
```

`ReservationConflictException`은 이미 저장된 예약 시간을 조회 단계에서 발견했을 때 사용하고, `ObjectOptimisticLockingFailureException`은 동시에 진행된 트랜잭션이 커밋 단계에서 충돌했을 때 사용한다.

---

# 6. 정리

- `@Version`은 스터디룸의 버전을 관리하고, 일반 조회만으로는 증가하지 않는다.
- `OPTIMISTIC_FORCE_INCREMENT`는 예약 생성 트랜잭션이 성공할 때 버전을 증가시켜 동시 요청 충돌을 감지한다.
- 예약 생성 로직은 기존 `Reservation` 저장과 응답 DTO 변환을 그대로 유지한다.
- 낙관적 락 동시성 테스트는 서비스 계층을 직접 호출해 성공 1건·충돌 1건·DB 저장 1건을 검증한다.
- 낙관적 락 충돌은 글로벌 예외 핸들러에서 409 Conflict 응답으로 처리한다.

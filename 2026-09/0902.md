# StudyOn 예약 중복 방지 DB 제약조건 정리

애플리케이션의 비관적 락만으로는 모든 중복 예약을 완전히 막는 최종 방어선이 되기 어렵다. 따라서 PostgreSQL의 배타 제약조건(Exclusion Constraint)을 `schema.sql`에 추가해, 같은 스터디룸에서 확정된 예약 시간이 겹치면 DB 자체가 저장을 거절하도록 구성했다.

---

# 1. 애플리케이션 락과 DB 제약조건의 역할

예약 생성 서비스에서는 스터디룸 행에 `PESSIMISTIC_WRITE` 비관적 락을 걸고 예약 중복 여부를 확인한다.

```text
요청 A → 스터디룸 행 잠금 → 중복 확인 → 예약 저장 → 커밋
요청 B → 잠금 해제까지 대기 → 중복 확인 → 충돌 응답
```

비관적 락은 일반적인 동시 요청을 순서대로 처리해 중복 예약을 예방한다. 다만 서비스 로직의 실수, 락을 거치지 않는 직접 SQL, 미래의 다른 예약 생성 경로까지 막으려면 DB 규칙도 필요하다.

```text
애플리케이션 비관적 락
→ 사용자에게 "이미 예약된 시간대"라는 정상적인 충돌 응답 제공

PostgreSQL 배타 제약조건
→ 어떤 경로로 INSERT하더라도 겹치는 확정 예약 저장 자체를 차단
```

---

# 2. 배타 제약조건 추가 SQL

PostgreSQL은 일반 제약조건에 `ADD CONSTRAINT IF NOT EXISTS` 문법을 제공하지 않는다. 그래서 시스템 카탈로그 `pg_constraint`에서 같은 이름의 제약조건이 있는지 먼저 확인하고, 없는 경우에만 추가한다.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

DO $$
BEGIN
    IF NOT EXISTS (
        SELECT 1
        FROM pg_constraint
        WHERE conname = 'ex_reservations_no_overlap'
          AND conrelid = 'reservations'::regclass
    ) THEN
        ALTER TABLE reservations
        ADD CONSTRAINT ex_reservations_no_overlap
        EXCLUDE USING gist (
            study_room_id WITH =,
            tsrange(start_at, end_at, '[)') WITH &&
        )
        WHERE (status = 'CONFIRMED');
    END IF;
END $$;
```

`btree_gist` 확장은 GiST 인덱스에서 `study_room_id WITH =` 비교를 사용할 수 있게 한다.

---

# 3. 시간 범위와 겹침 판별

`tsrange(start_at, end_at, '[)')`는 예약 시간을 PostgreSQL 시간 범위로 만든다.

```text
[) = 시작 시간 포함, 종료 시간 제외

10:00 ~ 11:00 → [10:00, 11:00)
11:00 ~ 12:00 → [11:00, 12:00)
```

`&&`는 두 범위가 겹치는지 확인하는 연산자다. 종료 시간이 다음 예약의 시작 시간과 같은 경우에는 겹치지 않으므로 연속된 예약은 가능하다.

```text
같은 방 10:00~11:00 + 11:00~12:00 → 가능
같은 방 10:00~12:00 + 11:00~13:00 → 불가
다른 방 10:00~12:00 + 10:00~12:00 → 가능
취소 예약 + 새 확정 예약             → 가능
```

`WHERE (status = 'CONFIRMED')` 조건 때문에 취소된 예약은 제약조건 검사 대상에서 제외된다.

# 4. 기존 데이터 충돌 확인

제약조건을 추가할 때 PostgreSQL은 이미 저장된 예약 행도 모두 검사한다. 기존에 같은 방·같은 시간대의 확정 예약이 있으면 제약조건 생성이 실패한다.

실제 오류에서는 스터디룸 2번에 아래 두 확정 예약이 이미 존재했다.

```text
16:00 ~ 19:00
16:00 ~ 17:00
```

테스트 DB라면 예약 데이터를 비운 뒤 제약조건을 다시 추가하는 방법이 가장 단순하다.

```sql
DELETE FROM reservations;
```

운영 데이터라면 삭제 전에 충돌 행을 조회하고, 잘못된 예약을 취소 처리하거나 관리자가 별도로 정리해야 한다.

```sql
SELECT id, study_room_id, start_at, end_at, status
FROM reservations
WHERE study_room_id = 2
  AND status = 'CONFIRMED'
ORDER BY start_at;
```

# 5. 예약 조회 인덱스

비회원 예약 조회 API는 이메일·전화번호로 조회한 뒤 최신 예약부터 보여준다.

```sql
CREATE INDEX IF NOT EXISTS idx_reservations_guest_lookup
    ON reservations (guest_email, guest_phone, created_at DESC);
```

이 인덱스는 아래 조회에 맞춰진다.

```sql
SELECT *
FROM reservations
WHERE guest_email = ?
  AND guest_phone = ?
ORDER BY created_at DESC;
```

인덱스 컬럼 순서는 `이메일 → 전화번호 → 생성일 내림차순`이며, `IF NOT EXISTS`는 같은 이름의 인덱스가 이미 있으면 생성 오류 없이 건너뛴다는 뜻이다.

---

# 6. 정리

- 비관적 락은 예약 서비스의 동시 요청을 순서대로 처리하고, DB 배타 제약조건은 중복 저장을 최종적으로 막는다.
- `tsrange(..., '[)')`와 `&&`를 사용하면 같은 방의 겹치는 예약만 차단하면서 연속 예약은 허용할 수 있다.
- 취소 예약은 배타 제약조건의 대상에서 제외해 같은 시간대 재예약이 가능하다.
- 기존 충돌 예약이 있으면 제약조건을 만들 수 없으므로, 테스트 DB는 데이터를 정리한 뒤 다시 실행해야 한다.
- 비회원 예약 조회에는 이메일·전화번호·생성일 순서의 복합 인덱스를 사용한다.

# 관리자 상세 통계와 대시보드 UI 개선

관리자 통계를 요약, 회원·이용 분석, 재료·냉파 분석, 레시피 분석으로 나누고 기간 조건에 따라 집계하도록 개선했다. 프런트는 기존 코드 구조를 유지하면서 카드·탭·표의 시각적 일관성을 높였다.

---

# 1. 관리자 상세 통계 구성

| 탭 | 주요 지표 |
| --- | --- |
| 통계 요약 | 평균 냉파 점수, 등록 재료, 만료 재료, 신규 레시피 |
| 회원·이용 분석 | 회원 변화, 냉장고·장보기·레시피 이용 회원 |
| 재료·냉파 분석 | 기간별 등록·만료 추이, 카테고리별 만료량, 최다 만료 재료 |
| 레시피 분석 | 등록 주체별 레시피 수, 카테고리별 레시피 수 |

같은 지표가 여러 탭에 중복되면 관리자가 어느 값을 봐야 하는지 혼란스러워진다. 평균 냉파 점수와 만료 건수처럼 중복된 카드는 한 위치에만 남겼다.

---

# 2. 기간별 집계 단위

조회 기간이 길어질수록 모든 날짜를 일별로 반환하면 응답 크기가 커지고 그래프가 읽기 어려워진다.

- 짧은 기간: 일별 집계
- 중간 기간: 주별 집계
- 긴 기간: 월별 집계

PostgreSQL의 `DATE_TRUNC`를 사용하면 날짜를 주 또는 월의 시작 시점으로 정규화할 수 있다.

```sql
SELECT CAST(DATE_TRUNC('week', ep.created_at) AS DATE) AS week_start,
       COUNT(*) AS count
FROM expired_products ep
WHERE ep.created_at >= :startAt
  AND ep.created_at < :endExclusive
GROUP BY DATE_TRUNC('week', ep.created_at)
ORDER BY week_start
```

`DATE_TRUNC('week', ...)`는 PostgreSQL에서 해당 날짜를 그 주의 월요일 00시 기준으로 맞춘다.

---

# 3. 이전 동일 기간 대비 증감률

사용자가 선택한 기간 길이만큼 바로 이전 기간을 계산해 현재 값과 비교했다.

예를 들어 8월 1일부터 8월 3일까지 선택했다면:

- 현재 기간: 8월 1일 ~ 8월 3일
- 이전 동일 기간: 7월 29일 ~ 7월 31일

```plain text
증감률 = (현재 값 - 이전 값) / 이전 값 × 100
```

이전 값이 0이면 0으로 나눌 수 없기 때문에 별도의 표시 규칙이 필요하다. 무조건 0%로 표시하기보다 “이전 기간 데이터 없음”처럼 의미를 명확히 전달하는 편이 안전하다.

---

# 4. 레시피 작성자 구분

`recipes.created_by`를 이용해 레시피 등록 주체를 구분한다.

- `created_by IS NULL`: 기본 제공 레시피
- 작성자가 `USER`: 회원 등록 레시피
- 작성자가 `ADMIN`: 관리자 등록 레시피

카테고리별 목록에서도 전체, 기본 제공, 회원 등록, 관리자 등록 필터를 제공해 같은 데이터를 관점별로 확인할 수 있게 했다.

---

# 5. 관리자 화면 디자인 정리

홈·회원·통계 화면의 카드, 탭, 입력 요소를 shadcn/ui 계열의 단정한 스타일로 맞췄다. 라이브러리를 새로 도입하기보다 기존 CSS와 컴포넌트 구조를 유지하면서 다음을 통일했다.

- 카드 테두리, 그림자, 둥근 모서리
- 탭의 활성·비활성 상태
- 버튼 높이와 색상
- 제목 및 보조 문구의 명암
- 표와 그래프 영역 간격

디자인 통일은 단순 장식보다 정보의 우선순위를 빠르게 파악하게 하는 것이 목적이다.

---

# 6. 정리

- 통계는 지표를 많이 추가하는 것보다 관리자 의사결정에 필요한 값만 남기는 것이 중요하다.
- 기간 길이에 따라 일·주·월 단위로 집계하면 응답과 화면을 함께 최적화할 수 있다.
- 이전 동일 기간 비교는 선택 기간과 동일한 길이로 계산한다.
- 같은 데이터가 여러 탭에 중복되지 않도록 역할을 분명하게 나눈다.

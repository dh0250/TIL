# 문의 챗봇 답변 판정 구조화와 OIDC 인증 방식 학습

문의 챗봇이 답변 가능 여부를 판정하는 방식을 텍스트 매칭에서 JSON 구조화 출력으로 바꾼 이유를 다시 정리했고, 최근 CI/CD에 붙인 OIDC(Role-to-Assume) 인증 방식도 함께 학습했다.

---

# 1. 답변 판정을 텍스트 매칭에서 JSON 구조화로 변경

문의 챗봇은 정책 문서에 근거가 없으면 답변을 거부해야 하는데, 초기 구현은 모델 응답에 `"CANNOT_ANSWER"`라는 문자열이 포함되어 있는지로 답변 가능 여부를 판정했다.

이 방식은 모델이 그 문구를 다른 문장 안에 섞어서 출력하거나 살짝 다르게 표현하면 판정이 어긋날 수 있다는 문제가 있었다. 예를 들어 모델이 "CANNOT_ANSWER 상태입니다"처럼 안내 문장 안에 섞어 쓰면 매칭 로직에 따라 오탐이 날 수 있고, 반대로 표현이 조금만 달라져도 판정을 놓칠 수 있었다.

이를 `{"answerable": bool, "answer": str}` 형태의 JSON 구조화 출력으로 바꿨다.

```python
def _parse_structured_output(raw_output: str) -> tuple[bool, str]:
    try:
        data = json.loads(raw_output)
        answerable = bool(data.get("answerable", False))
        answer = str(data.get("answer", "")) if answerable else ""
        return answerable, answer
    except (ValueError, TypeError, KeyError):
        return False, ""
```

파싱이나 포맷이 어긋나는 경우에도 `(False, "")`로 안전하게 폴백하도록 만들어서, 예외 상황에서 챗봇이 근거 없는 답을 내놓기보다 "답변 불가"로 처리되게 했다. 문자열 안에서 특정 문구를 찾는 방식보다 정해진 스키마로 값을 꺼내는 방식이 훨씬 예측 가능하다는 걸 체감했다.

# 2. GitHub Actions OIDC(Role-to-Assume) 인증 방식

배포 워크플로우 중 일부는 정적 Access Key 대신 OIDC 방식으로 AWS 자격 증명을 받는다. 두 방식의 차이를 정리했다.

| 방식 | 자격 증명 | 특징 |
| --- | --- | --- |
| 정적 Access Key | Repository Secret에 저장된 고정 키 | 키가 유출되면 만료 전까지 계속 악용될 수 있음 |
| OIDC(Role-to-Assume) | GitHub Actions가 발급한 단기 토큰으로 IAM Role을 임시로 위임받음 | 저장된 장기 키가 없고, 자격 증명이 워크플로우 실행 시간만큼만 유효함 |

OIDC 방식은 워크플로우에 `id-token: write` 권한을 주고, `aws-actions/configure-aws-credentials`가 GitHub의 OIDC 토큰으로 `sts:AssumeRoleWithWebIdentity`를 호출해 임시 자격 증명을 발급받는 구조다.

```yaml
permissions:
  contents: read
  id-token: write

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
      aws-region: ${{ env.AWS_REGION }}
```

AWS 쪽에는 IAM Role의 신뢰 정책(Trust Policy)에 GitHub의 OIDC Provider와 어떤 저장소/브랜치에서 온 요청만 이 Role을 위임받을 수 있는지 조건을 걸어둔다. 저장소에 고정 Access Key를 남기지 않아도 되고, 토큰이 워크플로우 실행 시간 동안만 유효하다는 점에서 정적 키를 그대로 쓰는 것보다 노출 위험이 작다.

---

# 3. 정리

- 답변 가능 여부 판정을 텍스트 매칭에서 JSON 스키마 기반 구조화 출력으로 바꾸면 모델 응답 형식이 조금 흔들려도 안정적으로 파싱할 수 있다.
- 파싱/포맷 예외는 "답변 가능"이 아니라 "답변 불가" 쪽으로 안전하게 폴백시키는 게 챗봇 신뢰성 측면에서 안전하다.
- OIDC(Role-to-Assume) 방식은 장기 Access Key를 저장소에 두지 않고, 임시 자격 증명으로 CI가 AWS 리소스에 접근하게 해준다.
- IAM Role의 신뢰 정책으로 어떤 저장소/브랜치만 Role을 위임받을 수 있는지 제한해두는 게 OIDC 구조의 핵심이다.

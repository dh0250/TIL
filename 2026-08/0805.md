# React + Spring Boot AWS 배포 (S3 + Elastic Beanstalk)

React(Next.js) 프런트엔드와 Spring Boot 백엔드를 GitHub Actions로 자동 빌드하여 AWS에 배포하는 과정을 정리. 프런트는 정적 빌드 후 **S3** 정적 호스팅에, 백엔드는 **Docker 이미지**로 빌드해 DockerHub에 올린 뒤 **Elastic Beanstalk(EB)** 단일 인스턴스에서 실행한다. 실습 코드는 `restaurant-frontend-main`, `restaurant-backend-main` 참고 (Next.js 16 / React 19 / Java 21 / Spring Boot 4.1 / Gradle 8.14.3 기준).

> 2025-07-15 이후 신규 AWS 계정은 EC2 750시간 프리티어 대신 최대 200달러 크레딧 + 최대 6개월 Free Plan 기준으로 바뀌었다.

---

# 1. Elastic Beanstalk란?

AWS가 제공하는 **관리형 PaaS(Platform as a Service)**로, 애플리케이션 배포와 확장성 관리를 간소화한 서비스다. 개발자가 서버 인프라를 세세하게 설정하지 않아도 코드(또는 이미지)를 업로드하기만 하면 실행에 필요한 환경을 자동으로 구성·관리해준다.

- **프로비저닝**: 필요한 컴퓨팅 리소스(서버·네트워크·소프트웨어)를 준비·설정
- **로드 밸런싱**: 여러 서버로 트래픽을 분산해 단일 서버 과부하 방지
- **자동 스케일링**: 트래픽에 따라 리소스를 자동으로 늘리거나 줄여 비용 절감
- **모니터링**: 성능을 지속적으로 관찰·기록해 문제를 신속히 감지

2011년 AWS가 출시했으며, 자동으로 자라나는 애플리케이션 환경을 마법의 콩나무(Beanstalk)에 비유한 이름이다.

**장점**: 간편한 사용(코드/이미지 업로드만 하면 나머지는 자동), 자동 스케일링, Java/.NET/PHP/Node.js/Python/Ruby/Go/Docker 등 다양한 스택 지원, 사용한 만큼만 과금.
**단점**: 세밀한 인프라 제어가 어려움, 자동 스케일링으로 인한 비용 예측 어려움, 학습 곡선 존재.

## 주요 개념

| 개념 | 설명 |
| --- | --- |
| 애플리케이션 | 환경·환경 구성·버전을 포함하는 EB 구성 요소의 논리적 모음 (폴더와 유사) |
| 애플리케이션 버전 | 배포 가능한 코드(WAR/JAR) 또는 이미지 정보가 담긴 S3 객체 |
| 환경 | AWS 리소스의 모음. 한 번에 하나의 애플리케이션 버전만 실행 |
| 환경 구성 | 환경과 리소스의 동작 방식을 정의하는 매개변수·설정 모음 |
| 저장된 구성 | 재사용 가능한 환경 구성 템플릿 |
| 플랫폼 | OS, 언어 런타임, 앱 서버, 웹 서버 등 EB가 제공하는 실행 스택 조합 |
| Host Manager(HM) | 각 EC2 인스턴스에서 실행되며 배포·메트릭 집계·로그 모니터링·패치를 담당 |

## 동작 흐름

1. **Create Application** — 버전·환경·구성을 담을 애플리케이션 생성
2. **Upload Version** — 실행 가능한 코드/이미지 정보를 업로드
3. **Launch Environment** — 업로드한 버전 기반으로 EC2 등 AWS 리소스를 자동 프로비저닝
4. **Manage Environment** — 모니터링, 로깅, 스케일링, 장애 대응
5. **Deploy New Version** — 새 버전을 최소 중단으로 배포
6. **Update Version** — 버그 수정·기능 추가에 따라 버전 갱신

## Well-Architected Framework (6 Pillars)

운영 우수성 / 보안 / 신뢰성 / 성능 효율성 / 비용 최적화 / 지속 가능성 — 클라우드 아키텍처를 설계할 때 고려해야 할 여섯 가지 기둥.

# 2. 전체 아키텍처

```plain text
[User Browser]
  ├── React/Next.js 정적 파일 → S3 Website (HTTP)
  └── Spring Boot API → Elastic Beanstalk Single instance → DockerHub Image
```

| 서비스 | 구성 | 설명 |
| --- | --- | --- |
| EC2 | 프리티어/크레딧 기준 인스턴스 | Spring Boot API 실행용 (EB가 내부적으로 생성) |
| S3 | 정적 웹 호스팅 | React 정적 빌드 파일 저장 |
| EBS | 30GB 루트 디스크 | EB에서 EC2 사용 시 자동 생성 |
| IAM | GitHub Actions 전용 사용자 | 최소 권한 정책으로 구성 |

# 3. 사전 준비 체크리스트

## IAM & 권한

- `github-actions-user` 등 GitHub Actions 전용 IAM 사용자를 생성하고, S3/Elastic Beanstalk 작업만 허용하는 **최소 권한 정책**을 부여한다.
- DockerHub를 사용하므로 `AmazonEC2ContainerRegistryFullAccess`는 필요 없다.
- 실습은 Access Key 방식을 쓰지만, 운영 환경 권장안은 **GitHub OIDC 기반 임시 자격증명**이다.
- GitHub Secrets에 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` 등록.

> ⚠️ IAM 사용자 권한이 부족하면 `iam:ListInstanceProfiles`, EB 서비스 역할(`aws-elasticbeanstalk-service-role`) Pass 권한 관련 에러가 날 수 있으니, 역할을 전달(pass role)할 수 있는 권한까지 챙겨야 한다.

## S3 버킷

- EB 배포용 ZIP 업로드 버킷(예: `my-eb-deploy-bucket`)과 React 정적 호스팅용 버킷을 별도로 준비한다.
- 정적 호스팅 버킷은 퍼블릭 읽기 권한 또는 CloudFront 연동으로 구성.
- GitHub Secrets: `S3_BUCKET_NAME`

## DockerHub

- 공개 리포지토리를 준비하고 GitHub Secrets에 `DOCKER_USERNAME`, `DOCKER_PASSWORD` 등록.

## Elastic Beanstalk 애플리케이션/환경

- 플랫폼: `Docker running on 64bit Amazon Linux 2023`
- 환경 유형: `Single instance` (ALB 미사용)
- 포트: `8080`
- 네트워킹/인스턴스 트래픽/업데이트·모니터링·로깅은 기본값 사용
- GitHub Secrets: `EB_APP_NAME`, `EB_ENV_NAME`

## 기타 Secrets & 보안 그룹

- `application-dev.yml`은 GitHub에 커밋하지 않고 **base64 인코딩**하여 `APPLICATION_DEV_YML` Secret으로 등록 후, CI에서 디코딩해 사용한다.
- Single instance 환경은 EB가 만든 프록시를 통해 접근하므로 보안 그룹은 실습에 필요한 포트만 열어두고, 수업/실습 종료 후 환경을 종료한다.

## 배포 후 헬스체크

- `http://EB환경주소/actuator/health/liveness` 요청 → 정상 시 `HTTP 200`, `{"status":"UP"}`
- DB 상태와 분리된 **애플리케이션 생존 확인**용 엔드포인트다.

# 4. CI/CD 전략과 GitHub Secrets

GitHub Actions로 테스트·빌드·배포를 자동화하며, `application-dev.yml` 같은 민감 설정은 커밋하지 않고 base64로 Secrets에 저장한다.

| 키 | 설명 |
| --- | --- |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | IAM 사용자 키 |
| `AWS_REGION` | 예: `ap-northeast-2` |
| `APPLICATION_DEV_YML` | base64 인코딩된 Spring 설정 |
| `S3_BUCKET_NAME` | React 배포용 버킷명 |
| `EB_APP_NAME` / `EB_ENV_NAME` | Spring Boot용 EB 애플리케이션/환경 이름 |
| `DOCKER_USERNAME` / `DOCKER_PASSWORD` | DockerHub 로그인 정보 |

> 실습 중 노출된 AWS Access Key 등 자격증명은 **즉시 폐기(rotate)**하고 절대 코드/문서에 평문으로 남기지 않는다.

# 5. React 배포 (S3)

S3 정적 배포에서는 React용 Dockerfile을 쓰지 않는다. `next.config.mjs`의 `output: "export"` 설정으로 `npm run build`를 실행하면 정적 산출물이 `out/`에 생성되고, 이를 그대로 S3에 동기화한다.

`restaurant-frontend-main/.github/workflows/frontworkflow.yml`:

```yaml
name: Deploy React to S3

on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Build static site
        env:
          NEXT_PUBLIC_API_BASE_URL: ${{ secrets.NEXT_PUBLIC_API_BASE_URL }}
        run: npm run build

      - uses: aws-actions/configure-aws-credentials@v6
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ secrets.AWS_REGION }}

      - name: Sync to S3
        env:
          S3_BUCKET_NAME: ${{ secrets.S3_BUCKET_NAME }}
        run: aws s3 sync out/ "s3://$S3_BUCKET_NAME" --delete
```

`main` 브랜치 push 시 의존성 설치 → lint → 정적 빌드 → AWS 자격증명 설정 → `aws s3 sync --delete`로 버킷 내용을 최신 빌드로 교체하는 흐름이다.

### 이미지 URL 처리 (`restaurant-frontend-main/src/utils/imageUtils.js`)

백엔드가 반환하는 이미지 경로가 상대경로/절대경로 어느 쪽이든 안전하게 처리하도록 유틸을 분리했다.

```javascript
const API_BASE_URL =
  process.env.NEXT_PUBLIC_API_BASE_URL || "http://localhost:8080";

export function resolveImageUrl(imageUrl) {
  if (!imageUrl) {
    return "";
  }

  // 이미 완성된 절대 URL이면 그대로 사용
  if (/^(https?:)?\/\//i.test(imageUrl) || /^(data|blob):/i.test(imageUrl)) {
    return imageUrl;
  }

  // 상대경로일 때만 백엔드 주소 추가
  return `${API_BASE_URL.replace(/\/$/, "")}/${imageUrl.replace(/^\/+/, "")}`;
}
```

기존에는 컴포넌트마다 `${NEXT_PUBLIC_API_BASE_URL}${productImageUrl}` 형태로 직접 문자열을 이어붙여, 이미 절대 URL인 이미지가 오면 깨지는 문제가 있었다. `resolveImageUrl`로 감싸 `<img src={resolveImageUrl(productImageUrl)} />` 형태로 통일했다.

# 6. Spring Boot 배포 (Elastic Beanstalk + DockerHub)

`restaurant-backend-main/Dockerfile`:

```docker
FROM eclipse-temurin:21-jre
COPY build/libs/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

`restaurant-backend-main/.github/workflows/workflow.yml`:

```yaml
name: Build and Push Spring Boot Docker Image to aws

on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  docker-build-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      - name: Set up Java
        uses: actions/setup-java@v5
        with:
          distribution: 'temurin'
          java-version: '21'
          cache: 'gradle'

      - name: Grant execute permission to gradlew
        run: chmod +x ./gradlew

      - name: Set YML
        env:
          APPLICATION_DEV_YML: ${{ secrets.APPLICATION_DEV_YML }}
        run: |
          mkdir -p src/main/resources
          echo "$APPLICATION_DEV_YML" | base64 --decode > src/main/resources/application-dev.yml

      - name: Build with Gradle
        run: ./gradlew clean build --no-daemon

      - name: Log in to DockerHub
        env:
          DOCKER_PASSWORD: ${{ secrets.DOCKER_PASSWORD }}
          DOCKER_USERNAME: ${{ secrets.DOCKER_USERNAME }}
        run: echo "$DOCKER_PASSWORD" | docker login -u "$DOCKER_USERNAME" --password-stdin

      - name: Build and Push Docker Image
        env:
          DOCKER_USERNAME: ${{ secrets.DOCKER_USERNAME }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t "$DOCKER_USERNAME/springboot-api:$IMAGE_TAG" .
          docker push "$DOCKER_USERNAME/springboot-api:$IMAGE_TAG"

      - name: Create Dockerrun.aws.json
        env:
          DOCKER_USERNAME: ${{ secrets.DOCKER_USERNAME }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          echo "{
            \"AWSEBDockerrunVersion\": \"1\",
            \"Image\": {
              \"Name\": \"$DOCKER_USERNAME/springboot-api:$IMAGE_TAG\",
              \"Update\": \"true\"
            },
            \"Ports\": [
              { \"ContainerPort\": \"8080\" }
            ]
          }" > Dockerrun.aws.json

      - name: Zip for deployment
        run : zip -r app.zip Dockerrun.aws.json

      - uses: aws-actions/configure-aws-credentials@v6
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ secrets.AWS_REGION }}

      - name: Upload to S3 and deploy to EB
        env:
          S3_BUCKET_NAME: ${{ secrets.S3_BUCKET_NAME }}
          EB_APP_NAME: ${{ secrets.EB_APP_NAME }}
          EB_ENV_NAME: ${{ secrets.EB_ENV_NAME }}
        run: |
          VERSION_LABEL=v${{ github.run_number }}-${{ github.run_attempt }}
          S3_KEY=deploy/$VERSION_LABEL.zip

          aws s3 cp app.zip "s3://$S3_BUCKET_NAME/$S3_KEY"

          aws elasticbeanstalk create-application-version \
            --application-name "$EB_APP_NAME" \
            --version-label "$VERSION_LABEL" \
            --source-bundle "S3Bucket=$S3_BUCKET_NAME,S3Key=$S3_KEY"

          aws elasticbeanstalk update-environment \
            --environment-name "$EB_ENV_NAME" \
            --version-label "$VERSION_LABEL"
```

흐름: base64로 저장해둔 `application-dev.yml`을 디코딩해 리소스에 배치 → Gradle 빌드 → DockerHub 로그인 후 `{DOCKER_USERNAME}/springboot-api:{commit sha}` 태그로 이미지 push → EB가 요구하는 `Dockerrun.aws.json`(이미지 이름 + 컨테이너 포트 8080)을 생성해 zip으로 묶음 → S3에 업로드 후 `create-application-version` + `update-environment`로 새 버전을 EB 환경에 배포한다. 버전 라벨은 `v{run_number}-{run_attempt}`로 매 실행마다 고유하게 생성해 EB 버전 이력과 매칭한다.

`application-dev.yml`은 로컬 개발용(백업)과 EB 배포용(샘플) 두 버전으로 나눠 관리한다. 배포용은 `spring.application.name`, `hibernate.dialect` 명시, `image.image-url`을 EB 환경 주소로 교체하는 정도가 차이점이며, **DB 접속 정보·JWT 서명 키 등 민감 값은 실제 커밋/문서에 평문으로 남기지 않고 GitHub Secrets(base64)로만 주입**한다.

# 전체 흐름 정리

1. **Elastic Beanstalk**는 코드/이미지를 업로드하면 EC2·로드밸런싱·오토스케일링·모니터링을 자동으로 구성해주는 관리형 PaaS이며, 애플리케이션(컨테이너) → 버전(S3 객체) → 환경(리소스 모음) 구조로 관리된다.
2. 이번 배포 아키텍처는 **React(Next.js) 정적 빌드는 S3**, **Spring Boot는 DockerHub 이미지를 EB Single instance**가 실행하는 이원화 구조다.
3. 사전 준비는 **IAM 최소 권한 사용자 → S3 버킷(배포용/호스팅용) → DockerHub 리포지토리 → EB 애플리케이션/환경(Docker on AL2023, Single instance, 8080 포트)** 순서로 진행하고, 필요한 값은 모두 GitHub Secrets에 등록한다.
4. **React 배포**는 `next build`(export) → `aws s3 sync --delete`로 끝나는 단순한 흐름이고, **Spring Boot 배포**는 Gradle 빌드 → Docker 이미지 push → `Dockerrun.aws.json` 생성 → S3 업로드 → `create-application-version`/`update-environment`로 EB에 새 버전을 반영하는 흐름이다(`restaurant-frontend-main`, `restaurant-backend-main`의 GitHub Actions 워크플로 실습).
5. 배포 후에는 `/actuator/health/liveness`로 헬스체크하고, `application-dev.yml`처럼 민감한 설정은 base64로 인코딩해 Secrets에만 저장하며 **AWS 자격증명 등은 코드/문서에 절대 평문으로 남기지 않는다.**

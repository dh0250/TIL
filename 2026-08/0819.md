# 모니터링 배포 자동화와 알림 규칙 정리

Monitoring 스택을 수동 배포에서 GitHub Actions 자동 배포로 전환하면서 겪은 문제들과, Prometheus 알림 규칙을 정리했다.

---

# 1. Monitoring 배포 자동화 워크플로우

그동안은 Monitoring EC2에 수동으로 접속해 설정을 갱신했는데, 반복되는 작업이라 GitHub Actions로 자동화했다.

```plain text
main 반영
→ docker compose config (문법 검증)
→ promtool check config / check rules (Prometheus 설정 검증)
→ compose.yaml, prometheus/, grafana/ 압축 (monitoring.tar.gz)
→ S3 업로드 (monitoring/{Git SHA}.tar.gz)
→ SSM send-command로 EC2에 배포 지시
→ EC2: releases/{Git SHA}에 압축 해제 → current 심볼릭 링크 교체 → docker compose pull && up -d
```

배포 전에 `docker compose config`와 `promtool check`로 설정 파일을 미리 검증하도록 넣었다. Prometheus 설정에 오타가 있으면 컨테이너가 떠 있어도 실제로는 지표를 못 모으는 상태가 될 수 있는데, 배포 단계에서 먼저 걸러내면 이런 상황을 줄일 수 있다.

SSM `send-command`는 실행 후 바로 끝나는 게 아니라서, 명령이 끝날 때까지 기다렸다가 결과를 확인하는 단계도 추가했다.

```bash
aws ssm wait command-executed \
  --command-id "$COMMAND_ID" \
  --instance-id "$INSTANCE_ID"

aws ssm get-command-invocation \
  --command-id "$COMMAND_ID" \
  --instance-id "$INSTANCE_ID"
```

# 2. docker compose 프로젝트 이름 고정

배포를 자동화한 뒤 이전 릴리스의 컨테이너가 정리되지 않고 그대로 남는 문제가 있었다.

원인은 Docker Compose가 프로젝트 이름을 명시하지 않으면 현재 작업 디렉터리 이름을 기준으로 프로젝트 이름을 정한다는 데 있었다. 배포 스크립트는 매번 `releases/{Git SHA}`라는 새 디렉터리를 만들고 `current` 심볼릭 링크로 연결하는 구조인데, Git SHA는 배포할 때마다 달라지므로 이 경로를 기준으로 프로젝트 이름이 결정되면 배포할 때마다 다른 프로젝트로 인식될 수 있다. `docker compose up -d --remove-orphans`는 같은 프로젝트 안에서 정의에서 빠진 컨테이너만 정리하기 때문에, 프로젝트 이름 자체가 매번 바뀌면 이전 릴리스의 컨테이너는 다른 프로젝트로 취급되어 정리 대상에서 빠졌다.

`compose.yaml` 최상단에 프로젝트 이름을 고정해서 해결했다.

```yaml
name: naengpa-monitoring

services:
  prometheus:
    image: prom/prometheus:v3.5.0
    ...
```

이렇게 하면 배포 디렉터리가 매번 바뀌어도 같은 프로젝트로 인식되기 때문에 `--remove-orphans`가 이전 릴리스의 컨테이너를 정확히 정리한다.

# 3. GitHub Actions STS 리전 엔드포인트 이슈

`aws-actions/configure-aws-credentials`로 OIDC(`role-to-assume`) 방식 인증을 붙였는데, 배포 워크플로우가 자격 증명 단계에서 계속 실패했다.

원인은 STS(Security Token Service) 글로벌 엔드포인트와 리전 엔드포인트 차이였다. 별도 설정이 없으면 STS 호출이 글로벌 엔드포인트(`sts.amazonaws.com`)로 나가는데, 계정/리전 설정에 따라 이 엔드포인트로의 `AssumeRoleWithWebIdentity` 호출이 막히거나 지연되는 경우가 있었다. 환경변수로 리전 엔드포인트를 명시적으로 쓰도록 지정해서 해결했다.

```yaml
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  env:
    AWS_STS_REGIONAL_ENDPOINTS: regional
  with:
    role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
    aws-region: ${{ env.AWS_REGION }}
```

`AWS_STS_REGIONAL_ENDPOINTS: regional`을 지정하면 STS 호출이 `sts.ap-northeast-2.amazonaws.com`처럼 해당 리전 엔드포인트로 나가서, 리전과 무관하게 항상 같은 글로벌 엔드포인트를 타던 문제가 사라졌다.

# 4. Prometheus 알림 규칙 추가

지표를 모으기만 하고 임계치를 넘었을 때 알려주는 규칙이 없어서, 서비스 다운/오류율/지연 3가지 축으로 알림 규칙을 추가했다.

```yaml
groups:
  - name: naengpa-service-alerts
    rules:
      - alert: SpringInstanceDown
        expr: up{job="spring-prod"} == 0
        for: 1m

      - alert: SpringHighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{job="spring-prod", status=~"5.."}[5m]))
          /
          clamp_min(sum(rate(http_server_requests_seconds_count{job="spring-prod"}[5m])), 0.000001)
          > 0.05
        for: 5m

      - alert: SpringHighLatency
        expr: |
          histogram_quantile(
            0.95,
            sum by (le) (rate(http_server_requests_seconds_bucket{job="spring-prod"}[5m]))
          ) > 1
        for: 5m
```

오류율 계산에서 분모가 0이 될 수 있어 `clamp_min(..., 0.000001)`으로 최솟값을 보정했다. 요청이 거의 없는 구간에서 분모가 0에 가까워지면 오류율이 비정상적으로 튀거나 계산 자체가 실패할 수 있는데, 아주 작은 값으로 하한을 걸어두면 이런 경우를 방지할 수 있다. `for: 1m`, `for: 5m`처럼 지속 시간을 조건에 넣은 것도, 순간적인 스파이크만으로 알림이 울리는 것을 막기 위해서다.

---

# 5. 정리

- Monitoring 배포를 설정 검증 → S3 업로드 → SSM 배포 지시 → EC2 반영 흐름으로 자동화했다.
- `docker compose`에 프로젝트 이름을 고정하지 않으면 릴리스 디렉터리가 바뀔 때마다 다른 프로젝트로 인식되어 컨테이너 정리가 안 될 수 있다는 걸 확인했다.
- GitHub Actions에서 OIDC 인증이 실패할 때 STS 리전 엔드포인트 설정을 의심해볼 수 있다는 걸 배웠다.
- Prometheus 알림 규칙에서 오류율처럼 나눗셈이 들어가는 식은 분모가 0이 되는 경우를 항상 고려해야 한다.

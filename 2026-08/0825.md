# 비회원 스터디룸 예약 서비스의 ERD와 동시성 설계

스터디온 프로젝트의 범위를 회원 서비스에서 비회원 예약 서비스로 줄이고, 화면과 DB 설계를 실제 필요한 기능에 맞게 정리했다. 이메일과 전화번호로 예약을 조회하고, 같은 스터디룸과 시간에 여러 요청이 들어와도 한 건만 성공시키는 것을 핵심 목표로 잡았다.

---

# 1. 비회원 예약 흐름

회원가입과 로그인 없이 예약할 때 다음 정보를 입력한다.

```text
이름
이메일
전화번호
스터디룸
시작 시간
종료 시간
이용 목적
```

예약조회에서는 이름을 다시 받지 않고 이메일과 전화번호가 모두 일치하는 예약을 최근 순서로 보여준다. 예약 직후의 **예약 조회하기** 버튼은 방금 생성한 예약을 바로 보여주고, 헤더의 일반 예약조회로 들어온 경우에만 이메일과 전화번호를 입력한다.

예약 비밀번호도 검토했지만, 예약마다 비밀번호가 다르면 한 사용자의 여러 예약을 한 번에 조회하기 어렵다. 이메일별 공통 비밀번호를 만들면 사실상 사용자 테이블과 비밀번호 관리가 필요해진다. 실제 공개 서비스가 아닌 학습용 프로젝트이므로 이메일과 전화번호 조회가 가장 단순한 선택이었다.

---

# 2. 기능 범위 단순화

프로젝트의 핵심이 동시성 학습이므로 현재 필요하지 않은 기능과 데이터를 제거했다.

- 회원가입, 로그인, Spring Security, JWT 제거
- 관리자 기능은 시간이 남으면 나중에 추가
- 이용 인원 선택 제거
- 예약코드 화면 표시 제거
- 예약 수정 제거: 변경하려면 취소 후 다시 예약
- 스터디룸 타입별 5개에서 3개로 축소
- 4·6·8·10인실 총 4가지 타입, 총 12개 운영
- 운영시간 06:00~23:00
- 예약은 1시간 단위, 최대 4시간

이용 인원을 예약에서 받지 않더라도 시설안내를 위해 `study_rooms.min_capacity`, `max_capacity`는 유지한다. 사용자가 방 종류를 보고 적합한 스터디룸을 선택하도록 한다.

---

# 3. 최소 ERD

현재 필요한 테이블은 `study_rooms`와 `reservations` 두 개다.

```text
study_rooms 1 ─── 0..N reservations
```

하나의 스터디룸에는 예약이 0개 이상 있을 수 있고, 하나의 예약은 반드시 하나의 스터디룸에 속한다. 실제 관계는 `reservations.study_room_id` 외래키로 연결한다.

## study_rooms

```text
id              BIGINT       PK
name            VARCHAR(50)  UNIQUE, NOT NULL
room_type       VARCHAR(20)  NOT NULL
min_capacity    INTEGER      NOT NULL
max_capacity    INTEGER      NOT NULL
open_time       TIME         NOT NULL
close_time      TIME         NOT NULL
active          BOOLEAN      NOT NULL
created_at      TIMESTAMP    NOT NULL
```

`room_type`은 값이 4개로 고정되어 있으므로 Java enum으로 관리하고 DB에는 문자열로 저장한다.

```java
public enum RoomType {
    FOUR_PERSON,
    SIX_PERSON,
    EIGHT_PERSON,
    TEN_PERSON
}
```

```java
@Enumerated(EnumType.STRING)
@Column(name = "room_type", nullable = false)
private RoomType roomType;
```

`EnumType.ORDINAL`은 enum 순서를 변경할 때 기존 데이터의 의미가 바뀔 수 있으므로 사용하지 않는다.

## reservations

```text
id              BIGINT        PK
study_room_id   BIGINT        FK, NOT NULL
guest_name      VARCHAR(50)   NOT NULL
guest_email     VARCHAR(255)  NOT NULL
guest_phone     VARCHAR(20)   NOT NULL
start_at        TIMESTAMP     NOT NULL
end_at          TIMESTAMP     NOT NULL
purpose         VARCHAR(50)   NOT NULL
status          VARCHAR(20)   NOT NULL
canceled_at     TIMESTAMP     NULL
created_at      TIMESTAMP     NOT NULL
```

이메일은 저장과 조회 시 앞뒤 공백을 제거하고 소문자로 정규화한다.

```java
String normalizedEmail =
    email.trim().toLowerCase(Locale.ROOT);
```

한국에서만 사용하는 개인 프로젝트이므로 PostgreSQL의 `TIMESTAMP`와 Java의 `LocalDateTime`을 사용하기로 했다.

# 4. 예약 상태와 취소

결제나 승인 과정 없이 생성 즉시 확정되므로 예약 상태는 두 개면 충분하다.

```java
public enum ReservationStatus {
    CONFIRMED,
    CANCELED
}
```

예약을 취소해도 행을 삭제하지 않는다.

```text
status       = CANCELED
canceled_at  = 취소한 시각
```

관리자와 회원 기능이 없기 때문에 모든 행에 같은 값만 들어갈 `created_by`, `updated_by`, `deleted_by`는 제거했다. 예약 수정 기능이 없고 취소 시각을 별도로 기록하므로 `updated_at`도 현재 범위에서는 필요하지 않다. 나중에 관리자 기능을 추가하면 Flyway의 새 버전에서 감사 컬럼을 추가할 수 있다.

# 5. DB 제약조건

```sql
CHECK (min_capacity > 0 AND max_capacity >= min_capacity);
CHECK (start_at < end_at);
CHECK (char_length(purpose) BETWEEN 1 AND 50);
CHECK (status IN ('CONFIRMED', 'CANCELED'));
```

다른 테이블의 수용 인원 컬럼을 예약 테이블의 CHECK 제약에서 직접 참조하기는 어렵다. 이용 인원을 받는 구조였다면 스터디룸을 조회한 뒤 서비스 계층에서 범위를 검증해야 하지만, 현재는 `headcount` 자체를 제거했다.

# 6. 예약 중복 확인과 인덱스

두 시간 범위는 다음 조건을 만족할 때 겹친다.

```sql
existing.start_at < requested.end_at
AND existing.end_at > requested.start_at
```

확정된 예약만 대상으로 조회한다.

```sql
SELECT 1
FROM reservations
WHERE study_room_id = :studyRoomId
  AND status = 'CONFIRMED'
  AND start_at < :requestedEnd
  AND end_at > :requestedStart
LIMIT 1;
```

사용자에게 특정 스터디룸의 예약 목록을 보여주는 기능은 없지만, 예약 화면의 시간 비활성화와 예약 생성 직전의 중복 검사를 위해 이 조회가 필요하다.

데이터가 많아지면 다음 인덱스를 추가할 수 있다.

```sql
CREATE INDEX idx_reservation_room_status_start
ON reservations (study_room_id, status, start_at);
```

인덱스 컬럼은 왼쪽부터 `study_room_id → status → start_at` 순서로 정렬된다. JPA 코드에서 인덱스 이름을 호출하는 것이 아니라 PostgreSQL이 쿼리 조건과 데이터 분포를 보고 자동으로 사용할지 결정한다. 데이터가 적으면 인덱스보다 전체 테이블을 읽는 `Seq Scan`이 더 빠를 수도 있다.

---

# 7. 비관적 락을 이용한 동시성 제어

중복 조회만 하고 예약을 저장하면 두 요청이 거의 동시에 들어왔을 때 둘 다 “예약 없음”을 확인한 후 저장할 수 있다. 이를 막기 위해 예약 생성 트랜잭션에서 대상 스터디룸 행을 비관적 락으로 잠근다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from StudyRoom s where s.id = :id")
Optional<StudyRoom> findByIdForUpdate(Long id);
```

```text
요청 A가 스터디룸 행 락 획득
→ 요청 A가 겹치는 예약 조회
→ 요청 A 예약 저장 및 커밋
→ 요청 B가 락 획득
→ 요청 B가 겹치는 예약 발견
→ 요청 B는 409 Conflict
```

예약 생성 전체를 하나의 `@Transactional` 범위로 묶어야 락이 중복 검사와 저장이 끝날 때까지 유지된다.

# 8. 백엔드 패키지 구조

현재 도메인이 두 개뿐이므로 기능별로 단순하게 나눈다.

```text
com.studyon
├── common
│   ├── config
│   └── exception
├── studyroom
│   ├── controller
│   ├── service
│   ├── repository
│   ├── domain
│   └── dto
└── reservation
    ├── controller
    ├── service
    ├── repository
    ├── domain
    ├── dto
    └── exception
```

구현체가 하나뿐인 서비스 인터페이스와 `ServiceImpl`, 미래를 위한 `auth`, `member`, `admin` 패키지는 미리 만들지 않는다.

---

# 9. 정리

- 비회원 예약은 이름·이메일·전화번호를 받고, 조회는 이메일과 전화번호로 한다.
- 스터디룸은 타입별 3개씩 총 12개이며 예약은 최대 4시간이다.
- 현재 ERD는 `study_rooms`, `reservations` 두 테이블이면 충분하다.
- 관리자·회원 기능이 없으므로 불필요한 감사·소프트 삭제 컬럼을 제거했다.
- 예약 취소는 삭제가 아니라 `CANCELED` 상태와 `canceled_at`으로 기록한다.
- 같은 시간의 동시 예약은 스터디룸 행 비관적 락과 중복 조회로 막는다.
- 인덱스는 SQL에서 직접 호출하지 않고 PostgreSQL 옵티마이저가 자동으로 선택한다.

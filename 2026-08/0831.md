# StudyOn 예약 서비스 테스트·Git 충돌 해결과 프로시저 학습 정리

StudyOn 예약 기능의 단위 테스트를 읽고 테스트 더블의 동작을 정리했다. 브랜치를 `dev` 기준으로 옮기는 과정에서 발생한 테스트 파일 충돌을 해결했고, 프로시저 방식의 별도 학습 프로젝트를 어떻게 분리할지도 정리했다.

---

# 1. 예약 시간 중복 확인 메서드

예약 생성 전에는 같은 스터디룸에서 확정된 예약과 시간이 겹치는지 확인한다.

```java
boolean existsByStudyRoomIdAndStatusAndStartAtLessThanAndEndAtGreaterThan(
        Long studyRoomId,
        ReservationStatus status,
        LocalDateTime endAt,
        LocalDateTime startAt
);
```

이 메서드는 조건에 맞는 예약 행이 하나라도 있으면 `true`를 반환한다.

```text
같은 스터디룸
AND CONFIRMED 상태
AND 기존 예약 시작 < 새 예약 종료
AND 기존 예약 종료 > 새 예약 시작
```

마지막 두 조건은 시간 구간이 하나라도 겹치는지 판별하는 표준 조건이다. 예를 들어 기존 예약이 10:00~12:00이고 새 예약이 11:00~13:00이면 두 조건을 모두 만족하므로 `true`가 된다.

# 2. Mockito given과 서비스 실행 결과의 차이

단위 테스트의 `given(...).willReturn(...)`은 mock 객체가 어떤 값을 반환할지 미리 준비하는 단계다.

```java
given(reservationRepository.findById(1L))
        .willReturn(Optional.of(reservation));
```

위 코드는 실제 DB를 조회하지 않고, 서비스가 `findById(1L)`을 호출했을 때 미리 만든 `reservation` mock을 돌려주도록 설정한다.

반면 아래 코드는 테스트 대상인 서비스를 실제로 호출한 결과다.

```java
ReservationCancelResponse response =
        reservationService.cancelReservation(1L, request);
```

흐름은 `given으로 가짜 데이터 준비 → 서비스 실행 → response로 결과 검증`이다.

`List.of(reservation)`은 예약 하나만 담은 리스트이므로, 조회 응답도 하나여야 한다는 의미로 아래 검증을 사용한다.

```java
assertThat(responses).hasSize(1);
```

# 3. verify의 의미

```java
verify(reservation).cancel();
```

이 코드는 `true`를 반환하는 조건문이 아니다. Mockito가 `reservation.cancel()`이 정확히 한 번 호출됐는지 검사한다.

```text
cancel() 호출됨     → 검증 통과, 다음 코드 실행
cancel() 호출 안 됨 → Mockito 검증 예외 발생, 테스트 실패
```

기본 의미는 다음과 같다.

```java
verify(reservation, times(1)).cancel();
```

단, `reservation`이 mock이므로 이 검증만으로 실제 엔티티 상태가 `CANCELED`로 변경됐는지는 확인하지 않는다. 서비스가 `cancel()`을 호출했는지만 검증한다.

# 4. 테스트 충돌 해결과 애플리케이션 이름 정리

`dev`를 기준으로 테스트 브랜치를 만든 뒤 기존 변경사항을 적용하는 과정에서 `ReservationServiceTest` 충돌이 발생했다. 예약 생성 테스트와 예약 조회·취소 테스트를 모두 포함하도록 파일을 합쳤다.

테스트 이름도 `@DisplayName`으로 한글 설명을 추가했다.

```text
예약 가능한 시간에는 예약을 생성한다
기존 예약과 시간이 겹치면 예약 생성을 거절한다
이메일과 전화번호를 정규화하여 예약 목록을 조회한다
예약자 정보가 일치하면 예약을 취소한다
예약자 정보가 일치하지 않으면 예약 취소를 거절한다
```

예전 프로젝트 이름이 남아 있던 `RoomitBackendApplicationTests`는 `StudyonBackendApplicationTests`로 변경했다. 충돌 해결 후 `./gradlew test` 전체 통과를 확인했고, 커밋과 푸시는 하지 않았다.

# 5. PostgreSQL 프로시저와 별도 학습 프로젝트

프로시저(Stored Procedure)는 DB 안에 SQL 작업 묶음을 저장해 두고 호출하는 방식이다. 예약 생성의 경우 중복 확인과 INSERT를 DB 안에서 함께 처리할 수 있다.

```text
Spring 서비스
→ PostgreSQL 프로시저/함수 호출
→ 스터디룸·운영시간·예약 중복 확인
→ 예약 INSERT
→ 결과 반환
```

기존 StudyOn 프로젝트는 그대로 두고, GitHub에서 받은 ZIP 복사본을 별도 폴더와 별도 레포로 분리해 프로시저 방식만 실험하기로 했다. 이 프로젝트처럼 예약 ID와 상태를 Spring으로 돌려받아야 하는 경우에는 반환값을 받기 쉬운 PostgreSQL 함수(function)가 프로시저보다 더 단순할 수 있다.

---

# 6. 정리

- 예약 중복 확인 `existsBy...` 메서드는 겹치는 확정 예약 행이 하나라도 있으면 `true`다.
- `given`은 mock의 반환값을 준비하고, 서비스 호출 결과는 `response`에 담아 검증한다.
- `verify(reservation).cancel()`은 `true` 반환이 아니라 메서드 호출 여부를 검증한다.
- 테스트 충돌을 해결하고 이전 Roomit 테스트 클래스명을 StudyOn으로 변경했다.
- 전체 Gradle 테스트가 통과했으며 커밋과 푸시는 하지 않았다.
- 프로시저 실험은 기존 프로젝트를 건드리지 않는 복사본에서 별도로 진행한다.

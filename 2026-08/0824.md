# 스터디온 프론트엔드 배포와 백엔드 실행 환경 학습

개인 프로젝트인 스터디온의 프론트엔드를 먼저 Vercel에 배포하면서 빌드와 환경변수의 역할을 정리했다. 이후 개발할 Spring Boot 백엔드의 환경별 설정, Docker, 포트 매핑, Nginx가 각각 어떤 역할을 하는지도 함께 학습했다.

---

# 1. Vercel 프론트엔드 배포

백엔드가 완성되지 않았어도 프론트엔드만 먼저 배포할 수 있다. 화면과 라우팅을 먼저 확인하고 다른 사람에게 공유할 수 있으며, 백엔드가 완성되면 API 주소만 연결하면 된다.

Vercel에서 GitHub 저장소를 가져오면 Next.js 프로젝트를 자동으로 감지하고 다음 과정으로 배포한다.

```text
GitHub 코드 가져오기
→ npm install
→ npm run build
→ 생성된 결과물을 Vercel에 배포
```

`npm run build`는 개발 서버를 실행하는 명령이 아니라 실제 배포가 가능한지 확인하고 최적화된 결과물을 만드는 명령이다. 로컬에서 빌드가 성공하면 문법 오류, 잘못된 import, 정적 페이지 생성 오류 등을 배포 전에 확인할 수 있다.

Vercel 프로젝트와 GitHub 저장소가 연결되어 있으면 `main` 브랜치에 push할 때 운영 배포가 자동으로 다시 실행된다. 다른 브랜치나 Pull Request는 Preview 배포로 확인할 수 있다.

`studyon-xxxx.vercel.app`처럼 뒤에 문자가 붙는 주소는 원하는 주소가 이미 사용 중이거나 Vercel이 중복을 피하기 위해 자동 생성한 것이다. 프로젝트의 **Settings → Domains**에서 사용 가능한 `vercel.app` 주소나 직접 구매한 도메인을 연결할 수 있다.

# 2. 프론트엔드 환경변수

`NEXT_PUBLIC_API_URL`은 브라우저에서 호출할 백엔드의 기본 주소다.

```env
NEXT_PUBLIC_API_URL=https://api.example.com
```

`NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저 코드에도 포함되므로 비밀번호나 API Secret을 넣으면 안 된다. 백엔드가 아직 없다면 당장 설정하지 않아도 되고, AWS 백엔드 주소가 정해진 뒤 Vercel 환경변수에 등록하면 된다.

```javascript
fetch(`${process.env.NEXT_PUBLIC_API_URL}/api/v1/study-rooms`);
```

# 3. Spring Boot 환경별 설정

같은 애플리케이션이라도 로컬 개발과 운영 환경에서는 DB 주소, 로그 수준, 외부 서비스 주소가 다르다. 이 값을 코드에 직접 넣지 않고 Spring Profile로 분리한다.

```text
application.yml
application-local.yml
application-prod.yml
```

```yaml
# application.yml
spring:
  profiles:
    active: local
```

```yaml
# application-local.yml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/studyon
```

```yaml
# application-prod.yml
spring:
  datasource:
    url: ${SPRING_DATASOURCE_URL}
```

`yml`과 `yaml`은 같은 YAML 형식이며 확장자만 다르다. 반면 `.env`는 `KEY=VALUE` 형태로 환경변수를 저장하는 파일이다. YAML은 애플리케이션의 계층형 설정에 적합하고, `.env`는 DB 비밀번호처럼 환경마다 달라지는 값을 전달할 때 주로 사용한다.

# 4. Docker와 포트 매핑

Docker는 애플리케이션과 실행에 필요한 Java 환경을 이미지로 묶어 어디서 실행하든 같은 환경을 제공한다. Docker 없이도 EC2에 Java를 설치하고 JAR를 직접 실행할 수 있지만, Docker를 사용하면 서버 설정 차이로 발생하는 문제를 줄이고 실행·교체 방법을 통일할 수 있다.

```dockerfile
FROM eclipse-temurin:21-jre
COPY build/libs/studyon.jar app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

```bash
docker run -p 8080:8080 studyon-backend
```

`-p 8080:8080`은 다음 의미다.

```text
내 컴퓨터 또는 EC2의 8080 포트
→ Docker 컨테이너 안의 8080 포트
```

컨테이너는 독립된 네트워크 공간을 사용하기 때문에 포트를 연결하지 않으면 외부에서 Spring Boot에 접근할 수 없다. 왼쪽은 외부 포트이고 오른쪽은 컨테이너 내부에서 Spring Boot가 사용하는 포트다.

# 5. Nginx의 역할

Nginx는 사용자의 HTTPS 요청을 받아 내부의 Spring Boot 서버로 전달하는 리버스 프록시로 사용할 수 있다.

```text
사용자
→ https://api.example.com
→ Nginx 443 포트
→ Spring Boot 컨테이너 8080 포트
```

Nginx는 HTTPS 인증서 처리, 도메인 연결, 요청 전달을 담당하고 Spring Boot는 예약 정책과 DB 처리를 담당한다. 개인 프로젝트 초기에는 Spring Boot를 직접 노출할 수도 있지만, HTTPS와 도메인을 적용할 때 Nginx를 두는 구조가 일반적이다.

# 6. 정리

- 백엔드가 없어도 프론트엔드를 먼저 Vercel에 배포할 수 있다.
- GitHub와 연결된 Vercel 프로젝트는 push할 때 자동으로 다시 배포된다.
- `npm run build`는 배포 가능한 최적화 결과물을 만들고 오류를 검사한다.
- `NEXT_PUBLIC_API_URL`은 브라우저가 호출할 백엔드 주소이며 Secret을 넣으면 안 된다.
- Spring Profile을 사용하면 로컬과 운영 환경의 DB·로그 설정을 분리할 수 있다.
- Docker는 동일한 실행 환경을 제공하고, 포트 매핑은 외부 포트와 컨테이너 포트를 연결한다.
- Nginx는 HTTPS 요청을 받아 Spring Boot로 전달하는 리버스 프록시 역할을 한다.

# Docker

컨테이너 기반 가상화 플랫폼인 도커의 개념(이미지·컨테이너)부터 설치, 기본 명령어, Dockerfile을 이용한 이미지 빌드, Docker Compose를 이용한 멀티 컨테이너 구성, Volume을 이용한 데이터 영속성까지 실습(`13_AWS/docker-compose`, `13_AWS/dockerpro`, `13_AWS/node-redis-app`)과 함께 정리.

---

# 도커(Docker)란?

리눅스 응용 프로그램을 프로세스 격리 기술로 컨테이너화하여 실행·관리하는 오픈 소스 컨테이너 가상화 플랫폼. 프랑스 PaaS 기업 닷클라우드의 내부 프로젝트로 시작해 2013년 3월 오픈 소스로 출시되었다.

- 리눅스의 **cgroups**, **커널 네임스페이스**, **OverlayFS/aufs** 같은 리소스 격리 기능을 이용해 하나의 리눅스 인스턴스 안에서 여러 독립 컨테이너를 실행한다. 가상 머신을 띄우고 유지보수하는 부담 없이 OS 수준 가상화를 제공한다.

| 구분 | 설명 |
| --- | --- |
| 이미지(Image) | 서비스 운영에 필요한 서버 프로그램, 소스코드·라이브러리, 컴파일된 실행 파일을 묶은 파일 묶음. DockerHub(github와 유사)를 통해 버전 관리·배포가 가능하다. |
| 컨테이너(Container) | 이미지를 실행한 상태. 애플리케이션과 종속성을 격리된 공간에서 프로세스로 동작시킨다. |

**도커의 장점**
- VM 없이 도커 엔진으로 동작해 성능이 좋고 메모리 사용량이 적다.
- 이미지 하나만 받으면 새 서버에서 바로 컨테이너를 생성할 수 있어 초기 세팅이 빠르고 실행 환경을 강제화할 수 있다.
- 모듈식 유닛 조합으로 개발 주기·기능 배포·버그 수정 속도가 빨라진다.

# 설치와 기본 사용

- Windows 10 기준 Docker Desktop은 Hyper-V 또는 **WSL2**(Windows Subsystem for Linux 2) 위에서 동작한다. Home/Pro 공통으로 쓸 수 있는 WSL2 방식으로 설치하는 것이 일반적이다.
- 이미지 저장소 역할을 하는 **Docker Hub**에 가입 후 `docker login`으로 로그인하면 원격 저장소의 이미지를 받아 쓸 수 있다.

hello-world 이미지로 기본 흐름을 확인한다.

```bash
$ docker pull hello-world        # 원격 저장소에서 이미지 다운로드 (run에도 pull이 포함됨)
$ docker images                  # 로컬 이미지 목록 확인
$ docker run --name hello hello-world   # 이미지로 컨테이너 생성 후 실행
$ docker ps -a                   # 모든 컨테이너 목록 확인 (Exited 상태 포함)
$ docker rm hello                # 정지된 컨테이너 삭제
$ docker rmi hello-world         # 컨테이너가 모두 삭제된 이미지 삭제
```

> `--name`을 지정하지 않으면 랜덤 이름이 부여되며, 다른 이름을 주면 같은 이미지로 여러 컨테이너를 동시에 만들 수 있다.

# 도커 기본 명령어

기본 구조: `$ docker [명령어] [옵션]`, 상세 사용법은 `$ docker [명령어] --help`로 확인.

**이미지 관련**

| 명령어 | 설명 |
| --- | --- |
| `docker search [이미지명]` | DockerHub에서 이미지 검색 (stars 순, OFFICIAL 이미지는 네임스페이스 생략) |
| `docker image pull [저장소명[:태그]]` | 이미지 다운로드 (태그 생략 시 `latest`) |
| `docker image ls` | 보유 이미지 목록 조회 |

**컨테이너 관련**

| 명령어 | 설명 |
| --- | --- |
| `docker container run [옵션] 이미지[:태그]` | 컨테이너 실행 |
| `docker container ls [-a]` | 실행 중(또는 전체) 컨테이너 목록 조회 |
| `docker container attach [이름]` | 실행 중인 컨테이너 내부로 진입 |
| `docker container stop / start / restart [이름]` | 컨테이너 정지 / 시작 / 재시작 |
| `docker container rm [-f] [이름]` | 컨테이너 삭제 (`-f`는 실행 중이어도 강제 종료 후 삭제) |

`run` 주요 옵션: `-d`(백그라운드), `-p 호스트포트:컨테이너포트`, `-it`(터미널 연결, `-i`+`-t`), `--rm`(종료 시 자동 파기), `--name`. 컨테이너 셸에서 나갈 때 `exit`(컨테이너 종료) 대신 `Ctrl+P,Q`를 쓰면 종료 없이 빠져나올 수 있고, 다시 들어갈 때는 `docker attach`를 쓴다.

**축약 명령어**

| full 명령어 | 축약 명령어 |
| --- | --- |
| `docker image pull` | `docker pull` |
| `docker image ls` | `docker images` |
| `docker container run` | `docker run` |
| `docker container start` | `docker start` |
| `docker container ls` | `docker ps` |
| `docker container stop` | `docker stop` |

**운용 명령어**: `docker container prune`(정지된 컨테이너 일괄 삭제), `docker image prune`(태그 없는 이미지 일괄 삭제), `docker system prune`(컨테이너·이미지·볼륨·네트워크 일괄 삭제), `docker container stats [이름]`(실시간 리소스 사용량).

# Dockerfile로 이미지 만들기

**Dockerfile 주요 명령어**

| 명령어 | 설명 |
| --- | --- |
| `FROM` | 베이스 이미지 설정 (`이미지:태그`) |
| `COPY` | 파일/디렉터리 복사. 절대경로만 가능, URL·압축해제 불가 |
| `ADD` | `COPY`와 유사하지만 상대경로·URL 사용 가능, 압축 파일은 자동 해제 |
| `RUN` | 이미지 빌드 과정에서 실행할 명령어 |
| `CMD` | 컨테이너 실행 시 기본 명령어. 여러 번 써도 마지막 것만 유효하며, `docker run`에 인자를 넘기면 덮어써진다 |
| `ENTRYPOINT` | 컨테이너 실행 시 항상 실행되는 명령어. `run`으로 인자를 넘겨도 그대로 유지된다 |
| `WORKDIR` | `COPY`/`RUN`/`CMD` 등이 수행될 기본 디렉터리 |
| `EXPOSE` | 컨테이너-호스트 연결 포트 지정 |
| `ENV` | 컨테이너 내부에서 쓸 환경 변수 (`$변수명`으로 참조) |
| `VOLUME` | 외부 파일 시스템 연결 |

Dockerfile은 확장자 없이 프로젝트 최상위 폴더에 만든다.

```bash
$ docker build -t {저장소이름}/{이미지이름}:{태그} {Dockerfile 위치}
# 이미지 이름은 소문자만 가능, 태그 미지정 시 latest
$ docker run -p {호스트포트}:{컨테이너포트} -d {이미지}:{태그}
```

주요 `run` 옵션: `-i`(표준입력 유지), `-t`(TTY 모드), `-d`(데몬 모드), `-p`(포트포워딩), `--rm`(종료 시 자동 삭제), `--restart=always`, `-v 호스트경로:컨테이너경로`(볼륨 마운트), `-e KEY=VALUE`(환경변수), `-u`(실행 계정), `-w`(작업 디렉터리).

배포 시: `docker login` → `docker push {이미지이름}`으로 Docker Hub에 업로드한다.

### 실습 — Spring Boot 이미지 (`13_AWS/dockerpro`, `docker-compose/chap01-boot-project`)

빌드 스테이지 없이 미리 빌드된 jar만 담는 단순 버전(`dockerpro/Dockerfile`):

```docker
FROM eclipse-temurin:21-jre
ARG JAR_FILE=build/libs/*.jar
COPY ${JAR_FILE} app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

Gradle 빌드까지 이미지 안에서 수행하는 **멀티 스테이지 빌드**(`chap01-boot-project/Dockerfile`):

```docker
FROM gradle:jdk21-alpine AS build
WORKDIR /app
COPY . .
RUN gradle clean build --no-daemon

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/build/libs/*.jar ./
RUN mv $(ls *.jar | grep -v plain) app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

빌드 스테이지(`gradle:jdk21-alpine`)에서 소스를 컴파일해 jar를 만든 뒤, 런타임 스테이지(`eclipse-temurin:21-jre-alpine`)에는 jar만 복사해 넣는다. `--no-daemon`은 매번 독립 JVM에서 빌드해 캐시가 이미지에 남지 않도록 하기 위함이고, 빌드 툴·소스가 최종 이미지에서 빠지므로 용량이 작고 보안 노출 면도 줄어든다.

### 실습 — Next.js 이미지 (`chap01-next-project/Dockerfile`)

의존성 설치(`dependencies`) → 빌드(`build`) → 실행(`production`) 3단계 멀티 스테이지로, Next.js의 standalone 출력만 최종 이미지에 담아 용량을 최소화한다.

```docker
FROM node:22-alpine AS dependencies
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=dependencies /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:22-alpine AS production
WORKDIR /app
ENV NODE_ENV=production
ENV HOSTNAME=0.0.0.0
ENV PORT=3000
COPY --from=build /app/public ./public
COPY --from=build --chown=node:node /app/.next/standalone ./
COPY --from=build --chown=node:node /app/.next/static ./.next/static
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

# Docker Compose

여러 컨테이너가 유기적으로 동작하는 애플리케이션을 하나의 **YAML** 설정 파일로 정의하고 한 번에 관리하는 도구. YAML은 Key-Value 구조이며 대소문자를 구분하고, 들여쓰기는 탭이 아닌 공백 2칸을 사용해야 한다.

**docker-compose.yml 주요 옵션**

| 옵션 | 설명 |
| --- | --- |
| `services` | Compose가 실행할 컨테이너 명세 (서비스명 ≠ 컨테이너명) |
| `image` | 사용할 이미지 지정 |
| `build` | Dockerfile 기반으로 이미지를 빌드해 사용 (`context`, `dockerfile`) |
| `command` | 컨테이너 시작 시 실행할 명령 |
| `ports` | `"호스트포트:컨테이너포트"` 포트포워딩 |
| `depends_on` | 서비스 기동 순서 지정 |
| `environment` | 환경 변수 설정 |
| `volumes` | `{볼륨명}:{경로}` 형태로 데이터 영속화 |
| `restart` | 재시작 정책 (예: `always`) |

**Compose 명령어**

```bash
$ docker-compose up [-d] [--build]     # 멀티 컨테이너 생성 및 실행
$ docker-compose ps / ls               # 컨테이너 조회
$ docker-compose run {서비스명} {명령}  # 컨테이너 내부에서 일회성 명령 실행
$ docker-compose start / stop {서비스명}
$ docker-compose logs -f {서비스명}    # 실시간 로그
$ docker-compose config                # 설정 확인
$ docker-compose down                  # 종료 및 삭제
```

### 실습 — Node.js + Redis (`13_AWS/node-redis-app`)

```dockerfile
# Dockerfile
FROM node:lts-alpine
WORKDIR /app
COPY app/ .
RUN npm install
CMD ["npm", "start"]
```

```yaml
# docker-compose.yml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - redis

  redis:
    image: redis:alpine
```

`app`은 로컬 Dockerfile로 빌드하고, `redis`는 공식 이미지를 그대로 사용한다. `depends_on`으로 redis가 먼저 뜬 뒤 app이 기동되며, 앱 코드에서는 `redis://redis:6379`처럼 서비스명을 호스트명으로 사용해 접속한다.

## Docker 네트워크

컨테이너 간 통신을 위해 호스트에 가상 네트워크 인터페이스를 만들어 연결하는 기능. 컨테이너는 각자 격리된 네트워크 샌드박스에서 실행되고, 엔드포인트를 통해 가상 네트워크에 연결되어 서비스 이름(DNS)으로 서로를 호출한다.

| 드라이버 | 설명 |
| --- | --- |
| bridge | 기본 브리지 네트워크. 동일 호스트 내 컨테이너를 격리된 가상 LAN으로 연결 |
| host | 호스트 네임스페이스 공유, 격리 없이 호스트 IP 직접 사용 |
| overlay | Swarm/Compose에서 다중 호스트 간 컨테이너 연결 |
| macvlan | 컨테이너에 별도 MAC 주소를 부여해 물리 네트워크에 직접 연결 |
| none | 네트워크 없이 완전 격리 |

Compose는 기본적으로 `프로젝트명_default` 브리지 네트워크를 자동 생성하지만, `networks:` 항목에 이름을 직접 정의하면 프로젝트 전체가 아닌 지정한 서비스만 묶어 격리를 강화할 수 있다.

### 실습 — 퍼블릭/프라이빗 네트워크 분리 (`13_AWS/docker-compose/docker-compose.yml`)

```yaml
services:
  backend:
    build: ./chap01-boot-project
    container_name: backend
    ports:
      - "8080:8080"
    networks:
      - app-public
      - app-private

  frontend:
    build: ./chap01-next-project
    container_name: frontend
    ports:
      - "3000:3000"
    depends_on:
      - backend
    networks:
      - app-public

  tester:
    image: alpine
    container_name: net-tester
    command: sleep 3600
    networks:
      - app-public

networks:
  app-public:
    driver: bridge
  app-private:
    driver: bridge
    internal: true
```

`backend`는 `app-public`(frontend와 통신용)과 `app-private`(외부에서 접근 불가, `internal: true`) 두 네트워크에 모두 속하고, `frontend`는 `app-public`에만 속해 backend와만 통신 가능하다. `tester`는 `alpine` 이미지로 `sleep 3600`만 실행하며 네트워크 연결 상태를 점검하는 용도로 붙여둔 컨테이너다. 이렇게 네트워크를 분리하면 프런트는 백엔드에 접근할 수 있지만 백엔드의 내부 전용 자원에는 접근하지 못하도록 격리할 수 있다.

# Volume & Container Modification

## Docker Volume

기본적으로 컨테이너가 삭제되면 파일 시스템도 함께 사라지는데, Volume을 사용하면 컨테이너 삭제 후에도 데이터가 호스트에 보존된다.

- **장점**: 데이터 영속성 유지, 코드/설정 파일 수정 시 컨테이너 재생성 없이 바로 반영(개발 생산성), 여러 컨테이너 간 데이터 공유.
- **Bind mount와의 차이**: Bind mount는 호스트의 특정 디렉터리를 그대로 마운트하는 반면, Volume은 Docker가 관리하는 별도 저장 공간이라 백업·이동·권한 관리에 유리하다.

```bash
$ docker volume create mysql_data
$ docker run -d -e MYSQL_ROOT_PASSWORD=my-secret-pw -v mysql_data:/var/lib/mysql --name mysql-container mysql:latest
$ docker volume ls                    # 볼륨 목록 조회
$ docker volume inspect mysql_data    # 세부 정보(JSON) 확인
$ docker volume rm mysql_data         # 특정 볼륨 삭제
$ docker volume prune                 # 사용하지 않는(연결 안 된) 볼륨 일괄 삭제
```

컨테이너를 `docker rm -f`로 삭제한 뒤 같은 볼륨을 마운트해 재생성해도 `testdb`의 데이터가 그대로 남아있는 것으로 영속성을 확인할 수 있다.

## Container Modification (컨테이너 개조)

기존 컨테이너에 패키지나 설정을 추가한 뒤 이를 새로운 이미지로 저장해, 자주 쓰는 설정이 포함된 커스텀 베이스 이미지를 만드는 작업.

```bash
$ docker run -it --name myubuntu ubuntu bash
$ apt update && apt install -y curl        # 컨테이너 내부에서 curl 설치
$ curl --version                           # 설치 확인
$ docker commit myubuntu ubuntu-with-curl  # 현재 상태를 새 이미지로 저장
$ docker run -it ubuntu-with-curl bash     # 새 이미지로 컨테이너 실행
```

# 전체 흐름 정리

1. 도커는 리눅스 커널의 격리 기능(cgroups, 네임스페이스)을 이용해 **이미지**(실행에 필요한 파일 묶음)를 **컨테이너**(격리된 프로세스)로 실행하는 가상화 플랫폼이며, VM보다 가볍고 빠르다.
2. `docker pull/run/ps/stop/rm/rmi` 같은 기본 명령어로 이미지-컨테이너 생명주기를 관리하며, `container`/`image` 서브커맨드와 축약형(`docker run` 등)이 함께 제공된다.
3. **Dockerfile**(`FROM`, `COPY`, `RUN`, `CMD`, `ENTRYPOINT` 등)로 커스텀 이미지를 빌드한다. 빌드 스테이지와 런타임 스테이지를 분리하는 **멀티 스테이지 빌드**를 쓰면 최종 이미지에서 빌드 툴·소스가 빠져 용량과 보안 노출을 줄일 수 있다(`13_AWS`의 Spring Boot·Next.js Dockerfile 실습).
4. 여러 컨테이너를 함께 운용해야 할 때는 **docker-compose.yml**로 서비스를 선언적으로 정의하고 `docker-compose up`으로 한 번에 띄운다. `depends_on`으로 기동 순서를, `networks`로 서비스 간 통신 범위를 제어한다(Node+Redis, backend/frontend 네트워크 분리 실습).
5. 컨테이너 삭제 후에도 데이터를 보존하려면 **Volume**을 마운트하고(`-v`), 실행 중인 컨테이너에 설치한 패키지를 재사용하려면 `docker commit`으로 새 이미지를 만든다.

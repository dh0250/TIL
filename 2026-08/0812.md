# AWS 배포 아키텍처와 컨테이너 배포 준비

냉파마스터의 Spring Boot, FastAPI, Next.js를 AWS에 배포하기 위해 VPC 네트워크, 보안 그룹, RDS, S3, ECR, Elastic Beanstalk의 역할을 정리하고 실제 리소스 구성을 시작했다.

---

# 1. 전체 요청 흐름

```plain text
사용자
→ Route 53
→ AWS Amplify(프런트엔드)
→ api 도메인
→ Application Load Balancer
   ├── /api/*   → Spring Boot :8080
   └── /agent/* → FastAPI :8000
→ RDS PostgreSQL :5432
```

사용자 브라우저는 FastAPI를 직접 호출하지 않는다. 문의 챗봇도 프런트 → Spring Boot → FastAPI 순서로 호출해 인증, 데이터 저장, 사용량 기록을 Spring Boot에서 통제한다.

---

# 2. VPC와 서브넷

VPC는 AWS 안에 만드는 프로젝트 전용 가상 네트워크다. `10.0.0.0/16`은 VPC 전체 주소 범위이고, 이 범위 안을 더 작은 서브넷으로 나눈다.

| 종류 | 예시 CIDR | 역할 |
| --- | --- | --- |
| Public 1 | `10.0.0.0/20` | ALB, AZ 2a |
| Public 2 | `10.0.16.0/20` | ALB, AZ 2b |
| Private App 1 | `10.0.128.0/20` | Spring/FastAPI, AZ 2a |
| Private App 2 | `10.0.144.0/20` | Spring/FastAPI, AZ 2b |
| Private DB | 사용하지 않는 VPC 내부 대역 | RDS |

다른 VPC와 CIDR이 같아도 서로 연결하지 않는다면 생성은 가능하다. 하지만 VPC Peering, Transit Gateway, VPN 등으로 연결할 계획이라면 주소가 겹치면 라우팅할 수 없으므로 처음부터 겹치지 않게 잡는 편이 안전하다.

가용 영역을 `ap-northeast-2a`, `ap-northeast-2b`로 나누는 이유는 한 데이터센터 영역에 장애가 발생해도 다른 영역에서 서비스를 계속할 수 있게 하기 위해서다.

---

# 3. 라우팅 테이블

라우팅 테이블은 서브넷에서 출발한 트래픽을 어디로 보낼지 결정하는 규칙표다.

- Public subnet: `0.0.0.0/0 → Internet Gateway`
- Private app subnet: 외부 접근이 필요하면 `0.0.0.0/0 → NAT Gateway`
- Private DB subnet: 인터넷으로 향하는 기본 경로 없이 VPC 내부 통신만 허용

Public/Private 여부는 이름이 아니라 연결된 라우팅 테이블과 퍼블릭 IP 설정으로 결정된다.

---

# 4. Security Group

Security Group은 EC2, ALB, RDS 같은 리소스에 적용하는 상태 저장형 방화벽이다. IP 전체를 열기보다 앞단 Security Group을 Source로 지정한다.

| Security Group | Inbound | Source |
| --- | --- | --- |
| ALB SG | 80, 443 | `0.0.0.0/0` |
| Spring SG | 8080 | ALB SG |
| FastAPI SG | 8000 | ALB SG 또는 Spring SG |
| RDS SG | PostgreSQL 5432 | Spring SG, 필요한 경우 FastAPI SG |

DB가 PostgreSQL이면 MySQL 3306 규칙은 만들 필요가 없다. FastAPI가 DB를 직접 사용하지 않는 구조라면 RDS SG에 FastAPI SG도 추가하지 않는다.

# 5. S3와 ECR 역할

## S3

파일 업로드, 배포 ZIP 등 객체 파일을 저장한다. 기존 버킷의 목적과 권한 정책이 다르면 배포 전용 버킷을 분리하는 편이 안전하다.

## ECR

Docker 이미지를 저장하는 AWS 컨테이너 레지스트리다.

- Spring Boot 이미지 저장소
- FastAPI Agent 이미지 저장소
- 이미지 스캔 활성화
- Lifecycle Policy로 오래된 이미지 정리
- `latest`만 사용하지 않고 Git Commit SHA 태그 사용
- 최근 정상 이미지를 남겨 롤백 가능하게 구성

Git SHA 태그는 ECR 화면이 아니라 GitHub Actions에서 Docker 이미지를 빌드하고 push할 때 지정한다.

# 6. FastAPI Dockerfile

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- `python:3.13-slim`: 가벼운 Python 3.13 기반 이미지
- `WORKDIR /app`: 컨테이너 작업 디렉터리
- `COPY requirements.txt`: 의존성 목록 먼저 복사
- `pip install --no-cache-dir`: 패키지 설치 후 캐시를 남기지 않음
- `COPY app ./app`: FastAPI 소스 복사
- `EXPOSE 8000`: 컨테이너 사용 포트 문서화
- `CMD`: Uvicorn으로 FastAPI 애플리케이션 실행

배포 이미지에는 개발용 `--reload`를 넣지 않는다.

# 7. DB 비밀 값 관리

RDS 주소, 사용자명, 비밀번호는 소스 코드나 GitHub 저장소에 저장하지 않고 AWS Secrets Manager에 보관한다.

```json
{
  "url": "jdbc:postgresql://RDS-ENDPOINT:5432/naengpa_db",
  "username": "DB_USER",
  "password": "DB_PASSWORD"
}
```

Elastic Beanstalk의 런타임 환경변수에 Secrets Manager ARN을 연결하면 Spring Boot는 기존 설정을 그대로 사용할 수 있다.

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
```

Elastic Beanstalk EC2 인스턴스 역할에는 해당 Secret에 대한 `secretsmanager:GetSecretValue` 권한이 필요하다.

# 8. Connection Pool

Connection Pool은 DB 연결을 매 요청마다 새로 만들지 않고 일정 개수를 미리 생성해 재사용하는 방식이다.

Spring Boot는 기본적으로 HikariCP를 사용한다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_MAXIMUM_POOL_SIZE:10}
      minimum-idle: ${DB_MINIMUM_IDLE:2}
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

최대 인스턴스 수 × 인스턴스별 최대 Pool 크기가 RDS의 최대 연결 수를 넘지 않도록 계산해야 한다. FastAPI가 DB에 직접 연결하지 않는다면 FastAPI용 SQLAlchemy Pool 설정은 필요하지 않다.

---

# 9. 정리

- ALB만 인터넷에 공개하고 애플리케이션과 DB는 Private subnet에 둔다.
- Security Group은 IP보다 다른 Security Group을 Source로 연결한다.
- Docker 이미지는 ECR에 저장하고 SHA 태그로 배포 버전을 식별한다.
- DB 자격증명은 Secrets Manager에서 관리한다.
- 운영 설정은 현재 구조에 실제로 필요한 것만 추가한다.

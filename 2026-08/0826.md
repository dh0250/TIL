# 영화 아카이브 TMDB 연동 설계와 HTTP 클라이언트·DB 선택

개인 프로젝트 movie-archive에서 TMDB API로 가져온 영화 데이터를 어떻게 시딩·동기화할지, 평점은 어느 쪽 데이터를 기준으로 삼을지를 구체화했다. 그 과정에서 WebClient의 동작 원리를 다시 짚어보다가 지금 프로젝트 구조(MVC, 블로킹)에는 맞지 않는다는 걸 확인하고 RestClient로 전환했고, DB도 MySQL에서 PostgreSQL로 바꿨다.

---

# 1. TMDB 데이터 시딩 전략

영화 데이터를 처음 채울 때는 다음 순서로 진행한다.

```text
1. /genre/movie/list 호출 → 장르 테이블 먼저 채움
2. /discover/movie?sort_by=popularity.desc 페이지네이션 → 영화 마스터 데이터 대량 수집
3. 응답의 genre_ids 배열 → MovieGenre 조인 테이블에 매핑
4. (선택) /movie/{id}/credits → 감독·배우 정보 추가 수집
5. tmdb_id 컬럼으로 원본 매핑 유지 → 중복 방지, 재동기화 기준
```

순서가 중요한 이유는 참조 무결성 때문이다. `/discover/movie` 응답에는 장르 이름이 아니라 `genre_ids: [28, 12]` 같은 ID 배열만 들어있어서, Genre 테이블이 먼저 채워져 있지 않으면 MovieGenre 매핑 자체가 불가능하다.

TMDB는 페이지당 20건을 반환하므로 500편을 모으려면 25페이지를 호출해야 한다. `total_pages` 값으로 상한을 걸고, 페이지 사이에 짧은 딜레이를 주는 게 안전하다.

`/movie/{id}/credits`는 영화 1편당 요청 1번이 추가로 드는 엔드포인트라 rate limit에 걸리기 쉽다. 검색·리뷰 기능에 필수가 아니므로 우선순위를 낮게 잡고 나중에 배치로 채우는 쪽으로 정리했다.

---

# 2. 정기 동기화 배치 설계

초기 시딩 이후에는 전체 카탈로그를 매번 다시 훑을 필요가 없다. TMDB에 새로 올라오는 신작만 계속 확인하면 되는데, "신작 추가"와 "기존 최신작 정보 갱신"을 별도 배치로 나누지 않고 하나로 합칠 수 있다.

```java
@Scheduled(cron = "0 0 3 * * MON")
public void syncRecentMovies() {
    // primary_release_date.gte = 최근 1~2개월 개봉작만 조회
    var recentMovies = tmdbClient.discoverRecentMovies();
    movieService.upsertByTmdbId(recentMovies); // tmdbId 있으면 갱신, 없으면 신규 저장
}
```

오래된 영화는 메타데이터가 거의 안 바뀌므로 대상에서 아예 제외한다. `primary_release_date.gte`로 최근 개봉작만 범위를 좁혀두면, "메타데이터가 실제로 바뀔 가능성이 있는 영화"와 "이 배치가 건드리는 영화"가 자연스럽게 겹치게 되어 불필요한 API 호출이 발생하지 않는다.

개봉일이 밀리거나, 초기엔 없던 한국어 번역이 나중에 채워지거나, 포스터가 정식 이미지로 교체되는 경우가 실제로 메타데이터가 바뀌는 사례다.

# 3. 평점을 자체 서비스 값으로 설계한 이유

"영화 리뷰·평점 서비스"인데 평점을 TMDB 데이터에서 그대로 가져오면 서비스 정체성과 맞지 않는다는 문제의식에서 출발했다. Letterboxd 같은 실제 리뷰 서비스도 IMDb·로튼토마토 점수를 노출하지 않고 자체 커뮤니티 평점만 보여준다.

그래서 TMDB의 `vote_average`, `vote_count`는 아예 저장하지 않기로 했다. 평점은 전적으로 사용자 리뷰(`Review.rating`)로 계산되는 `Movie.averageRating`이 유일한 기준이다.

```text
Movie
- popularity       (TMDB 제공, 참고용, 화면 노출 안 함)
- averageRating    (우리 서비스 리뷰 평균)
- reviewCount      (우리 서비스 리뷰 개수)
```

`averageRating`, `reviewCount`는 리뷰가 생성·수정·삭제될 때마다 갱신하는 비정규화 방식을 쓴다. 매번 `AVG()` 집계 쿼리를 날리는 대신 쓰기 시점에 미리 계산해두면, 영화 목록을 평점순으로 정렬할 때 집계 쿼리 없이 바로 컬럼 정렬만 하면 된다.

Review는 `(member_id, movie_id)`에 유니크 제약을 걸어 한 사람당 한 영화에 리뷰 하나만 허용하는 정책으로 정리했다.

# 4. TMDB popularity 필드의 의미

`popularity`는 평점이 아니라 "지금 얼마나 화제성이 있는지"를 나타내는 지표다. TMDB 공식 문서 기준으로 다음 요소를 조합해 매일 재계산된다.

```text
당일 투표 수
당일 조회수
당일 즐겨찾기 등록 수
당일 찜(watchlist) 등록 수
개봉일
누적 투표 수
전날의 popularity 점수
```

평점은 낮아도 화제성이 커서 popularity가 높을 수 있고, 반대로 평점은 높은데 오래된 영화라 popularity는 낮을 수도 있다. 그래서 이 값은 화면에 "평점"으로 노출하지 않고, 리뷰가 아직 없는 신작을 초기 화면에 어떤 순서로 보여줄지 정하는 내부 정렬용 참고 지표로만 쓰기로 했다.

# 5. WebClient와 비동기·논블로킹

블로킹 방식(`RestTemplate`)은 요청을 보낸 스레드가 응답이 올 때까지 그 자리에서 멈춰 기다린다. 그동안 그 스레드는 다른 요청을 처리할 수 없다.

논블로킹 방식(`WebClient`)은 요청을 보낸 스레드가 응답을 기다리지 않고 바로 다른 일을 하러 간다. 응답이 도착하면 콜백 형태로 이어서 처리한다. 서버가 동시에 처리할 요청이 많을수록 차이가 커지는데, 블로킹은 요청마다 스레드를 하나씩 점유한 채 대기시키므로 스레드 풀이 금방 고갈될 수 있고, 논블로킹은 적은 스레드로 훨씬 많은 동시 요청을 처리할 수 있다.

```java
tmdbWebClient.get()
    .uri(...)
    .retrieve()
    .bodyToMono(String.class)
    .block();   // 논블로킹 흐름을 여기서 강제로 블로킹처럼 되돌림
```

`.block()`을 호출하면 WebClient 내부는 논블로킹으로 동작해도, 호출부 입장에서는 결과가 올 때까지 기다리는 동기 방식처럼 쓰이게 된다. MVC(서블릿) 기반 프로젝트에서는 컨트롤러 자체가 동기적으로 동작하므로 이렇게 쓰는 게 자연스럽지만, 논블로킹의 성능 이점은 실제로 누리지 못하는 구조다.

# 6. spring-webflux 의존성이 실제로 하는 일

Spring Boot에서 앱이 MVC로 동작할지 WebFlux로 동작할지는 **스타터**가 결정한다.

```text
spring-boot-starter-webmvc     → Tomcat, 서블릿 기반, 스레드당 요청 하나
spring-boot-starter-webflux    → Netty, 전 구간 논블로킹
```

`org.springframework:spring-webflux`는 스타터가 아니라 그 안에 정의된 `WebClient`, `Mono`, `Flux` 같은 **클래스만 클래스패스에 올려주는 라이브러리**다. `spring-boot-starter-webmvc`가 이미 있는 프로젝트에 이 라이브러리만 추가해도 Spring Boot는 여전히 서블릿 기반 앱으로 판단해 Tomcat을 그대로 띄운다. 즉 자동 설정이나 내장 서버 교체는 전혀 일어나지 않고, `WebClient`라는 클래스 하나를 도구로 가져다 쓸 수 있게 될 뿐이다.

진짜 리액티브 전환은 스타터를 바꾸는 것 외에도 컨트롤러가 `Mono`/`Flux`를 반환하도록 바꾸고, DB 접근도 JPA(블로킹) 대신 R2DBC(논블로킹)로 바꿔야 하는 훨씬 큰 작업이다.

# 7. HTTP 클라이언트 비교와 RestClient로 전환

Java/Spring 진영에서 자주 쓰이는 HTTP 클라이언트를 정리하면 다음과 같다.

```text
RestTemplate   - Spring 구형, 블로킹, 유지보수 모드
RestClient     - Spring 6.1+, 블로킹, WebClient와 비슷한 빌더 문법
WebClient      - 논블로킹, WebFlux용으로 설계됨
HttpClient     - JDK 11+ 표준 라이브러리, 별도 의존성 불필요
OkHttp         - 서드파티, 안드로이드 쪽에서 특히 많이 씀
Apache HttpClient - 세밀한 커넥션/타임아웃 설정에 강함
OpenFeign      - 인터페이스 + 애노테이션 기반 선언형 클라이언트
```

지금 프로젝트는 JPA, Security, 컨트롤러 전부 블로킹 기반이라, 논블로킹용으로 설계된 WebClient를 `.block()`으로 억지로 동기처럼 쓰는 것보다 처음부터 동기로 설계된 RestClient가 더 맞는 선택이다. RestClient는 WebClient와 거의 같은 문법을 쓰면서도 `spring-webflux` 의존성도, `.block()`도 필요 없다.

```java
// 변경 전
tmdbWebClient.get().uri(...).retrieve().bodyToMono(String.class).block();

// 변경 후
tmdbRestClient.get().uri(...).retrieve().body(String.class);
```

`build.gradle`에서 `spring-webflux` 의존성을 제거하고, `TmdbConfig`/`TmdbClient`의 Bean 타입을 `WebClient` → `RestClient`로 교체했다.

# 8. DB 선택: PostgreSQL vs MySQL

처음엔 MySQL로 시작했다가 PostgreSQL로 바꿨다. 결정적인 이유는 `pg_trgm`(trigram 유사도 검색)으로 Elasticsearch 도입 **이전**의 검색 baseline을 만들 수 있다는 점이다.

```text
1단계: PostgreSQL + QueryDSL
2단계: pg_trgm으로 유사 검색 실험 (ILIKE, 유사도 매칭)
3단계: Elasticsearch(Nori) 추가
4단계: 검색 품질·응답 시간 비교
```

이 프로젝트의 원래 목표가 "왜 RDB 검색만으로는 부족하고 Elasticsearch가 필요한지 증명하는 것"이었는데, `pg_trgm` 기반 baseline이 있어야 그 비교가 수치로 설득력을 가진다. PostgreSQL 기본 full text search(`tsvector`)는 한국어 형태소 분석 사전이 기본 내장돼 있지 않아서, 한국어 비교 실험에는 `tsvector`보다 문자 단위 유사도인 `pg_trgm` 쪽이 더 적절한 baseline이 된다.

JSONB는 PostgreSQL의 강점 중 하나로 자주 언급되지만, Movie/Genre/Review처럼 정형화된 관계형 스키마에서는 활용도가 크지 않아 이번 프로젝트에서는 적극적으로 쓸 계획은 없다.

`build.gradle`의 `com.mysql:mysql-connector-j`를 `org.postgresql:postgresql`로, `compose.yaml`의 mysql 서비스를 postgres 서비스로 교체했다.

# 9. 정리

- TMDB 시딩은 장르 → 영화 마스터 데이터 → genre_ids 매핑 → (선택) credits → tmdb_id로 중복 방지 순서로 진행한다.
- 정기 동기화는 전체 카탈로그가 아니라 최근 개봉작만 훑어 신작 추가와 정보 갱신을 하나의 upsert 배치로 처리한다.
- 서비스 평점은 TMDB `vote_average`가 아니라 자체 리뷰(`Review.rating`)로 계산한 `averageRating`을 유일한 기준으로 삼는다.
- TMDB `popularity`는 평점이 아니라 화제성 지표이며, 화면에는 노출하지 않고 신작 초기 정렬에만 참고용으로 쓴다.
- WebClient는 논블로킹으로 설계됐지만 `.block()`을 쓰면 사실상 동기처럼 동작하며, 논블로킹의 성능 이점을 실제로 누리려면 프로젝트 전체가 리액티브 스택이어야 한다.
- `spring-webflux` 라이브러리 추가는 WebClient 클래스만 가져오는 것이지, 스타터를 바꾸지 않는 한 앱을 리액티브로 만들지 않는다.
- 지금 프로젝트(MVC + JPA, 블로킹)에는 WebClient보다 동기용으로 설계된 RestClient가 더 맞아 전환했다.
- PostgreSQL을 선택한 이유는 `pg_trgm` 기반 검색 baseline으로 Elasticsearch 도입 전후를 수치로 비교할 수 있기 때문이다.

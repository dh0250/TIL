# PostgreSQL DB 덤프를 이용한 개발 데이터 공유

냉파마스터 프로젝트의 데이터베이스 상태를 다른 환경에서도 재현할 수 있도록 PostgreSQL DB를 SQL 형식으로 덤프하고 압축 파일로 정리했다. 이 과정에서 덤프 파일의 구성과 복원할 때 주의할 점을 학습했다.

---

# 1. PostgreSQL DB 덤프 생성

데이터베이스의 테이블 구조와 데이터를 함께 옮기기 위해 `pg_dump`로 SQL 덤프를 생성했다.

```bash
pg_dump \
  --username=naengpa \
  --clean \
  --create \
  --file=naengpa_db.sql \
  naengpa_db
```

`--clean`은 기존 객체를 먼저 삭제하는 구문을 포함하고, `--create`는 데이터베이스 생성 구문까지 덤프에 넣는다. 덤프 파일에는 `DROP DATABASE`, `CREATE DATABASE`, `\\connect`가 포함되므로 빈 데이터베이스뿐 아니라 기존 환경도 같은 상태로 다시 구성할 수 있다.

다만 이 덤프를 복원하면 기존 `naengpa_db`가 삭제되므로, 운영 DB가 아닌 로컬 또는 별도 테스트 환경인지 먼저 확인해야 한다.

---

# 2. 덤프 파일 압축과 내용 확인

생성된 SQL 파일은 약 2.1MB였고, 저장과 전달이 편하도록 ZIP으로 압축했다.

```bash
zip naengpa_db.zip naengpa_db.sql
unzip -l naengpa_db.zip
```

압축 파일 안에는 `naengpa_db.sql` 하나만 포함되도록 구성했다. SQL은 텍스트 파일이라 압축 효율이 좋지만, ZIP 파일 자체는 바이너리라 Git에서 줄 단위 변경 내용을 확인할 수 없다. 데이터가 자주 바뀌는 파일이라면 저장소에 계속 새 버전을 쌓기보다 S3 같은 별도 저장소에 보관하는 편이 적합하다.

---

# 3. 덤프 복원 방법

이번 덤프는 PostgreSQL의 plain SQL 형식이므로 `pg_restore`가 아니라 `psql`로 복원해야 한다.

```bash
unzip naengpa_db.zip
psql --username=naengpa --dbname=postgres --file=naengpa_db.sql
```

SQL 내부에서 `naengpa_db`를 생성한 뒤 해당 DB로 다시 연결하므로, 처음에는 대상 DB가 아닌 `postgres` 같은 관리용 DB에 접속해야 한다.

또한 덤프에는 검색 성능 개선에 사용하는 `pg_trgm` 확장 생성 구문이 포함되어 있다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA public;
```

따라서 복원 계정에는 데이터베이스와 확장을 생성할 권한이 필요하다. PostgreSQL 버전이나 계정 권한이 다르면 복원이 중간에 실패할 수 있으므로, 복원 후에는 테이블과 확장 설치 여부를 확인해야 한다.

```bash
psql --username=naengpa --dbname=naengpa_db \
  --command="\\dt" \
  --command="\\dx pg_trgm"
```

---

# 4. 덤프 파일을 공유할 때 주의할 점

DB 덤프에는 스키마뿐 아니라 회원 정보, 결제 식별자처럼 외부에 노출되면 안 되는 데이터가 들어갈 수 있다. 저장소에 올리기 전 실제 운영 데이터인지 확인하고, 공유가 필요하다면 민감 정보는 익명화해야 한다.

또한 애플리케이션의 접속 비밀번호 같은 환경설정 값은 덤프에 포함하지 않고 환경변수로 관리해야 한다. DB 상태를 재현하는 파일과 DB에 접속하기 위한 비밀값은 서로 분리해서 다루는 것이 중요하다.

---

# 5. 정리

- `pg_dump`의 plain SQL 형식은 내용을 직접 확인할 수 있고 `psql`로 복원한다.
- `--clean`, `--create`가 포함된 덤프는 기존 DB를 삭제할 수 있으므로 복원 대상을 반드시 확인해야 한다.
- `pg_trgm` 같은 PostgreSQL 확장이 포함된 경우 복원 계정의 권한과 설치 결과도 확인해야 한다.
- DB 덤프를 공유하기 전 민감 데이터 포함 여부를 점검하고, 필요하면 익명화해야 한다.
- 자주 변경되는 바이너리 압축 파일은 Git보다 별도 객체 저장소에서 버전을 관리하는 편이 적합하다.

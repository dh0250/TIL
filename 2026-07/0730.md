# Agent 안전 제어와 Plan-Execute-Replan Workflow (D_10_Agentic, D_11_Workflow)

Checkpointer로 Thread별 대화 기억을 유지하는 Agent에 이어, 재시도·Fallback·Handoff 같은 안전 규칙을 모델이 아니라 LangGraph의 State와 Edge가 강제하도록 만드는 방법을 확인. 이후 Pydantic으로 검증되는 Plan 계약을 LLM Planner가 생성하고, Executor가 Task를 순서대로 실행·검증한 뒤 실패 원인에 따라 Replanner가 retry 또는 stop을 판단하는 Plan-Execute-Replan Workflow까지 실습.

---

# Checkpointer로 Thread별 대화 기억 유지 (05_agent_memory.py)

`InMemorySaver`를 Checkpointer로 연결해 같은 `thread_id`의 이전 메시지에서 이름·동행인·예산을 기억하고, 다른 `thread_id`에는 그 정보가 전혀 없음을 대조.

```python
agent = create_agent(
    model=ChatOpenAI(model="gpt-4o-mini", temperature=0),
    tools=[recommend_destination],
    checkpointer=InMemorySaver(),
    system_prompt=(
        "2. 현재 Thread의 대화에서 가장 최근 이름, 동행인, 전체 예산을 찾는다.\n"
        "3. 세 정보가 모두 있을 때만 Tool을 호출한다.\n"
        "5. 사용자가 정보를 수정하면 가장 최근 값을 사용한다."
    )
)
```

- `thread_config(thread_id)`로 만든 `{"configurable": {"thread_id": ...}}`가 Checkpointer가 대화를 구분하는 단위가 된다.
- 정보만 전달하는 Turn("이름은 수진이고 아이와 여행해, 예산은 20만원")에서는 아직 추천 요청이 아니므로 Tool을 호출하지 않아야 한다.
- 짧은 추천 요청 한 문장만으로도 Agent가 같은 Thread의 이전 메시지에서 이름·동행인·예산을 찾아 `recommend_destination` 인자를 채운다.
- 예산을 15만원으로 수정한 뒤에는 가장 최근 값이 Tool 인자에 반영되어, State가 단순 누적이 아니라 최신값 우선임을 보여준다.
- 다른 `thread_id`(student-2)에는 같은 Checkpointer를 쓰더라도 이전 대화가 전혀 없으므로, Agent는 정보를 추측하지 않고 다시 질문한다.

# 재시도 · Fallback · Handoff를 Graph Edge로 강제하기 (06_agent_safety.py)

FOUND/NOT_FOUND/TIMEOUT/AUTH_ERROR라는 결과 코드에 따라 재시도할지, 포기(Fallback)할지, 담당자에게 넘길지(Handoff)를 모델의 판단이 아니라 결정적인 State와 조건부 Edge로 강제.

```python
def route_after_search(state: SafetyState) -> Literal[...]:
    result = state["latest_result"]
    if result == "FOUND":
        return "finalize_success"
    if result in NON_RETRYABLE_RESULTS:
        return "finalize_handoff"
    if result in RETRYABLE_RESULTS and state["attempts"] < state["max_attempts"]:
        return "search_destination"
    return "finalize_fallback"
```

- `FOUND`는 즉시 `finalize_success`로, `AUTH_ERROR` 같은 재시도 불가 오류는 시도 횟수와 무관하게 곧바로 `finalize_handoff`로 분기한다.
- `NOT_FOUND`/`TIMEOUT`은 `max_attempts` 안에서만 재시도되고, 한도에 도달하면 `finalize_fallback`으로 빠진다 — 재시도 여부를 모델이 아니라 `route_after_search`가 결정한다.
- 종료 Edge가 없는 `build_broken_graph`는 `search_destination -> search_destination` 자기 순환만 있어, `recursion_limit=5`에 도달하면 `GraphRecursionError`로 강제 종료된다. 업무 로직이 아니라 실행 엔진의 최종 방어선임을 보여준다.
- 통합 Graph에서는 실제 `ChatOpenAI`가 `destination_lookup` Tool을 호출하고, `guard` Node가 `ToolMessage` 문자열 접두어(FOUND/NOT_FOUND/TIMEOUT/AUTH_ERROR)를 읽어 `ResultCode`로 변환한 뒤 `attempts`를 늘린다.
- `route_after_guard`는 `guard`가 만든 State만 보고 Agent 재호출/Fallback/Handoff를 결정하므로, 모델이 만든 자연어 답변과 무관하게 재시도 여부가 결정적으로 통제된다. 실제로 broad 재검색 성공, 두 번 실패 후 fallback, `AUTH_ERROR` 즉시 handoff 세 시나리오로 검증했다.

# Pydantic으로 Plan 계약 검증하기 (l_01_plan.py, travel_domain.py)

LLM Planner가 만든 Plan을 실행하기 전에, 등록되지 않은 Task 이름과 중복 Task를 Pydantic Validator로 차단해 계약을 위반한 Plan이 Executor에 도달하지 못하게 함.

```python
class Plan(BaseModel):
    goal: str = Field(min_length=5)
    tasks: list[TaskName] = Field(min_length=1, max_length=5)
    success_criteria: list[str] = Field(min_length=1)

    @field_validator("tasks")
    @classmethod
    def require_unique_tasks(cls, tasks: list[TaskName]) -> list[TaskName]:
        if len(tasks) != len(set(tasks)):
            raise ValueError("Plan에는 같은 Task를 중복할 수 없습니다.")
        return tasks
```

- `TaskName`은 `Literal`로 등록된 5개 Task(`requirements`, `weather`, `destination`, `budget`, `compose`)만 허용해, `"search_everything"`처럼 존재하지 않는 Task 이름은 `ValidationError`로 즉시 차단된다.
- `require_unique_tasks` Validator는 같은 Task가 중복 선택되어 불필요하게 반복 실행되는 것을 Plan 생성 단계에서 막는다.
- `generate_plan`은 `ChatOpenAI.with_structured_output(Plan)`으로 LLM 응답 자체를 Plan Schema로 강제하고, 다시 `Plan.model_validate`를 통과시켜 이중으로 검증한다.
- 코드 주석에 남은 설계 판단: 모든 요청이 항상 destination → budget 순서라면 고정 Workflow로 충분하지만, weather/destination/budget/compose 필요 여부가 요청마다 달라지므로 LLM Planner가 필요하다.

# Executor가 Plan을 실행하고 Validator가 결과를 검사 (l_02_executor.py, component1.py)

Plan에 담긴 Task 순서대로 등록된 실행 함수를 호출해 공유 Context에 결과를 쌓고, Validator가 각 Task의 실행 여부와 최종 일정 조건을 함께 검사.

```python
TASK_HANDLERS = {
    "requirements": execute_requirements,
    "weather": execute_weather,
    "destination": execute_destination,
    "budget": execute_budget,
    "compose": execute_compose,
}

def execute_plan(request, plan):
    context: Context = {}
    for task in plan.tasks:
        TASK_HANDLERS[task](request, context)
    if "draft" not in context:
        raise ValueError("전체 일정 Plan에는 compose Task가 필요합니다.")
    return context, context["draft"], path
```

- `Plan.tasks` 순서대로 `TASK_HANDLERS`를 순회하며 같은 `Context` dict에 결과를 누적하므로, 뒤 Task(`budget`, `compose`)는 앞 Task(`destination`)가 채운 Context 값을 그대로 읽는다.
- `compose` Task가 Plan에 없으면 `context["draft"]`가 없어 `execute_plan`이 즉시 `ValueError`를 던져, Executor 단계에서부터 불완전한 Plan을 조기에 걸러낸다.
- `validate_execution`은 두 층으로 검증한다: Plan에 포함된 각 Task의 실행 결과(Context 키)가 실제로 존재하는지, 그리고 `compose`가 있으면 `validate_draft`로 날씨·아이 동반·예산 같은 업무 조건까지 검사한다.
- `l_02_executor.py`의 Graph는 `executor -> validator -> END`로 끝나는 단순 선형 구조이며, 실패했을 때 재시도하는 로직은 아직 없다(재시도는 `l_03_replanner.py`에서 추가).

# Validator 실패 시 Replanner가 retry / stop을 판단 (l_03_replanner.py, component2.py)

`l_02_executor.py`의 선형 Graph에 Replanner Node와 조건부 Edge를 추가해, 검증 실패 원인에 따라 Plan을 수정해 재시도하거나 더 이상 해결할 수 없으면 멈추도록 확장.

```python
class ReplanDecision(BaseModel):
    action: Literal["retry", "stop"]
    reason: str
    plan: Plan | None = None

    @model_validator(mode="after")
    def require_plan_for_retry(self) -> "ReplanDecision":
        if self.action == "retry" and self.plan is None:
            raise ValueError("retry에는 수정 Plan이 필요합니다.")
        return self

def after_validation(state: WorkflowState) -> Literal["replanner", "__end__"]:
    if state["validation"].passed:
        return END
    if state["retries"] >= state["max_retries"]:
        return END
    return "replanner"
```

- `ReplanDecision.action`이 `"retry"`인데 `plan`이 없으면 `require_plan_for_retry` Validator가 즉시 `ValueError`를 던져, "재시도하라면서 새 Plan은 안 주는" 모순된 LLM 응답을 구조 단계에서 차단한다.
- `after_validation`은 검증 통과(`passed`) 또는 `retries`가 `max_retries`에 도달하면 곧바로 `END`로 보내고, 그 외의 실패만 `replanner`로 넘긴다 — 재시도 여부와 횟수 제한은 Edge가 강제하므로 예산 초과 같은 실패를 LLM이 무한정 재시도할 수 없다.
- `after_replan`은 `replanner`의 `action`이 `"retry"`일 때만 `executor`로 되돌리고 `"stop"`이면 `END`로 보낸다.
- 예산 5만원처럼 Plan을 아무리 바꿔도 해결 불가능한 조건에서는 Replanner가 `action="stop"`을 반환해야 하고, `requirements`/`weather` Task 누락처럼 Plan으로 해결 가능한 실패에서는 `action="retry"`와 수정된 Plan을 반환해야 한다.

# 전체 흐름 정리

1. Checkpointer는 `thread_id` 단위로 대화를 저장해, 같은 Thread에서는 이전 정보를 Tool 인자로 재사용하고 다른 Thread에는 정보를 노출하지 않으며, State에 최신값을 반영하도록 지시하면 옛 값이 아닌 최근 값으로 Tool을 호출한다.
2. 재시도·Fallback·Handoff 같은 안전 규칙은 모델의 자연어 판단이 아니라 Graph의 State 필드(`attempts`, `max_attempts`, `latest_result`)와 조건부 Edge가 결정적으로 강제해야 하며, 종료 Edge가 없는 Graph는 `recursion_limit`가 최종 방어선이 된다.
3. Plan은 LLM이 자유 형식으로 만드는 것이 아니라 Pydantic Schema(등록된 Task만 허용, 중복 금지)로 계약을 걸어, 위반된 Plan이 Executor에 도달하기 전에 차단한다.
4. Executor는 Plan의 Task 순서대로 실행 함수를 호출해 공유 Context에 결과를 쌓고, `compose`가 없으면 즉시 예외를 던져 불완전한 실행을 조기에 걸러낸다.
5. Validator는 "Task가 실행됐는가"와 "최종 결과가 업무 조건을 만족하는가"를 서로 다른 층에서 검사하고, 실패 시 Replanner가 재계획 가능 여부(retry)와 불가능 여부(stop)를 구조화된 결정으로 반환한다.
6. Plan-Execute-Validate-Replan 네 Node를 잇는 조건부 Edge(`after_validation`, `after_replan`)가 재시도 횟수와 종료 조건을 강제해, 해결 불가능한 실패에서 Agent가 무한히 반복하지 않도록 만든다.

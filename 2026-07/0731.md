# LangSmith Trace와 Dataset Evaluation으로 Workflow 검증하기 (D_12_Langsmith)

D_11_Workflow의 Plan-Execute-Validate Graph를 그대로 가져와 각 Task 함수를 `@traceable` Tool Run으로 감싸고, 실제 LangSmith 서버에 실행 경로와 실패 원인을 Trace로 기록. 이어서 baseline(destination 누락) Plan과 fixed Plan을 같은 Dataset·Evaluator로 각각 Experiment 평가해 두 버전의 결과를 LangSmith에서 비교할 수 있게 만듦.

---

# LangSmith 환경 변수 점검 (01_setup_check.py)

`.env`에 필요한 세 값(`LANGSMITH_API_KEY`, `LANGSMITH_TRACING`, `LANGSMITH_PROJECT`)이 모두 있는지, 값 형식이 올바른지 실제 업로드 전에 확인.

```python
def langsmith_setting_errors() -> list[str]:
    errors = [
        f"{name} 누락"
        for name in LANGSMITH_REQUIRED
        if not os.getenv(name)
    ]
    tracing = os.getenv("LANGSMITH_TRACING", "").strip().lower()
    if tracing and tracing not in {"true", "1", "yes", "on"}:
        errors.append("LANGSMITH_TRACING은 true여야 합니다.")

    api_key = os.getenv("LANGSMITH_API_KEY", "").strip().lower()
    if api_key.startswith("your_"):
        errors.append("LANGSMITH_API_KEY를 실제 Key로 변경하세요.")
    return errors
```

- `masked()`는 API Key 원문 대신 앞 4자리와 뒤 4자리만 보여줘, 콘솔에 값이 전부 노출되는 것을 막는다.
- `LANGSMITH_API_KEY`가 `"your_"`로 시작하면 템플릿 값을 그대로 두고 실행한 것으로 간주해 별도 오류로 안내한다.
- `--run` 옵션을 붙이면 `Client().info`를 호출해 실제 네트워크 연결까지 확인하고, 옵션이 없으면 환경 변수 형식만 검사한다.
- 이 검사 함수(`require_langsmith_settings`)는 이후 모든 스크립트(02~06)에서 실제 Trace를 기록하기 전에 공통으로 재사용된다.

# Task 함수를 @traceable Tool Run으로 감싸기 (workflow_components.py)

D_11_Workflow의 `execute_requirements`, `execute_weather` 등 순수 함수를 그대로 재사용하되, 각각을 `@traceable(run_type="tool")`으로 한 번 더 감싸 LangSmith에서 개별 Tool Run으로 보이게 만듦.

```python
@traceable(name="task-destination", run_type="tool")
def traced_destination(request: TripRequest, context: Context) -> dict[str, Any]:
    execute_destination(request, context)
    return {
        "destinations": [place.model_dump() for place in context["destinations"]]
    }

@traceable(name="d-travel-workflow", run_type="chain")
def run_workflow(inputs: dict, version: PlanVersion = "fixed") -> dict:
    ...
    result = build_workflow(version).invoke(
        {"goal": goal, "request": request, "path": []},
        config={"run_name": f"d-{version}-workflow"},
    )
```

- `TASK_HANDLERS`는 D_11_Workflow의 `execute_*` 대신 `traced_*` 함수를 등록해, `execute_plan`이 그대로 재사용되면서도 각 Task 실행이 LangSmith Trace Tree의 하위 Run으로 남는다.
- `run_workflow`는 `run_type="chain"`으로 전체 Planner → Executor → Validator 호출을 최상위 Run으로 묶고, `config={"run_name": ...}`으로 LangGraph `invoke` 자체도 버전별 이름을 갖는다.
- `baseline_target`/`fixed_target`은 `run_workflow`를 `langsmith_extra`의 `metadata`·`tags`만 다르게 호출하는 얇은 Wrapper로, Dataset 평가(`client.evaluate`)가 받는 Target 함수 형태(`inputs -> outputs`)에 맞춘다.
- `workflow_evaluator`는 단순 PASS/FAIL 일치뿐 아니라, PASS 기대 사례는 `selected_place`가 실제로 채워졌는지, FAIL 기대 사례는 실패 사유 문자열에 기대 키워드가 포함되고 "Task 누락"으로 인한 우연한 FAIL이 아닌지까지 함께 검사한다.

# LLM Planner로 실제 Trace 기록하기 (02_trace_workflow.py)

고정 Plan(`fixed_target`) 대신 `--llm` Flag로 `l_01_plan.py`의 실제 `ChatOpenAI` Planner를 호출해, LLM이 만든 Plan까지 포함한 전체 실행을 `tracing_context(enabled=True)` 안에서 LangSmith에 업로드.

```python
with tracing_context(enabled=True):
    result = (
        run_workflow(inputs, version="llm", langsmith_extra={...})
        if args.llm
        else fixed_target(inputs)
    )
```

- `tracing_context(enabled=True)`는 `.env`의 `LANGSMITH_TRACING` 설정과 무관하게 이 블록 안에서만 명시적으로 Trace 업로드를 켠다.
- `--llm`을 쓰려면 `OPENAI_API_KEY`도 있어야 하므로, `require_langsmith_settings()`와 별개로 이 조건을 스크립트 시작 시 따로 검사한다.
- 실행 후 `Plan`, `Path`(Planner → Executor → 각 Task → Validator 순서), `Draft`, `Validation`을 콘솔에 출력해, LangSmith 대시보드의 Trace Tree와 로컬 출력을 대조할 수 있게 한다.

# baseline Plan 실패를 Trace로 재현 (03_trace_failure.py)

`destination` Task가 빠진 baseline Plan을 평가해 Validator FAIL을 Trace로 남기고, `--runtime-error`로는 `compose` Task 자체가 없는 Plan을 실행해 `execute_plan`이 던지는 `ValueError`가 LangSmith에 예외 Run으로 기록되는 상황을 재현.

```python
if args.runtime_error:
    try:
        with tracing_context(enabled=True):
            run_workflow(inputs, version="runtime_error", langsmith_extra={...})
    except ValueError as exc:
        print("[Error]")
        print(type(exc).__name__ + " : ", exc)
    raise RuntimeError("runtime_error Plan이 예상한 ValueError를 만들지 않았습니다.")
```

- `version="runtime_error"`는 `workflow_components.make_plan`에서 `requirements, weather, destination, budget`만 있고 `compose`가 빠진 Plan을 만들어, `execute_plan`이 `context["draft"]`를 찾지 못해 `ValueError`를 던지도록 의도적으로 구성한 Plan이다.
- `except ValueError`로 예외를 잡아 콘솔에 출력하지만, 그 뒤의 `raise RuntimeError(...)`가 try/except 블록 바깥(if 블록과 같은 들여쓰기)에 있어 예외를 잡았는지 여부와 무관하게 항상 실행된다 — 즉 `--runtime-error`로 실행하면 `ValueError` 메시지를 출력한 뒤에도 스크립트는 결국 `RuntimeError`로 종료된다.
- `--runtime-error` 없이 실행하면 `baseline_target`으로 `destination` Task가 빠진 Plan을 평가해, 예외 없이 `Validation`에 실패 조건이 담긴 정상적인 FAIL 결과를 출력한다.

# WORKFLOW_VERSION 스위치로 baseline → fixed 디버깅 (04_debug_and_fix.py)

파일 상단의 `WORKFLOW_VERSION` 리터럴 하나만 바꿔 같은 입력에 대해 baseline과 fixed Plan의 결과 차이를 비교하는 디버깅 스크립트.

```python
# WORKFLOW_VERSION: Literal["baseline", "fixed"] = "baseline"
WORKFLOW_VERSION: Literal["baseline", "fixed"] = "fixed"

target = baseline_target if WORKFLOW_VERSION == "baseline" else fixed_target
with tracing_context(enabled=True):
    result = target(inputs)
```

- `baseline_target`은 `destination` Task가 없어 `context["destinations"]`를 못 채우고, Validator가 이를 "Task의 실행 결과가 없습니다" 류의 실패 조건으로 잡아 `passed=False`를 반환한다.
- `WORKFLOW_VERSION`을 `"fixed"`로 바꾸면 `destination` Task가 포함된 Plan이 실행되어 `selected_place`가 채워지고 Validation이 통과하는 것을, 코드 한 줄 수정만으로 LangSmith Trace 비교를 통해 확인할 수 있다.
- `print_result`는 Plan, Path, 선택 장소, Validation을 동일한 형식으로 출력해 두 버전을 나란히 비교하기 쉽게 만든다.

# LangSmith Dataset 만들고 baseline Evaluate (05_dataset_evaluation.py)

`EVALUATION_CASES` 세 사례(정상 통과 2건, 예산 초과로 FAIL 1건)를 LangSmith Dataset으로 등록하고, `client.evaluate`로 baseline Plan Target에 대해 Experiment를 실행.

```python
def ensure_dataset(client: Client) -> None:
    if client.has_dataset(dataset_name=DATASET_NAME):
        print(f"기존 Dataset을 사용합니다: {DATASET_NAME}")
        return
    client.create_dataset(DATASET_NAME, description="여행 workflow 평가 테스트용")
    client.create_examples(dataset_name=DATASET_NAME, examples=EVALUATION_CASES)

client.evaluate(
    baseline_target,
    data=DATASET_NAME,
    evaluators=[workflow_evaluator],
    experiment_prefix=BASELINE_EXPERMIMENT_PREFIX,
    max_concurrency=1,
    metadata={"version": "baseline", "lesson": "test-evaluation"}
)
```

- `--create-dataset`과 `--evaluate-baseline`은 `add_mutually_exclusive_group(required=True)`로 묶여 있어, 둘 중 정확히 하나만 지정해야 실행된다.
- `baseline_experiment_names`는 `reference_dataset_name=DATASET_NAME`으로 이미 실행된 baseline Experiment를 조회해, `--evaluate-baseline`을 여러 번 실행해도 같은 Experiment가 중복 생성되지 않도록 막는다.
- `EVALUATION_CASES`의 세 번째 사례(예산 5만원)는 `outputs.expected_failure_keyword`로 "예산 50,000원을 초과"라는 구체적 실패 문구까지 지정해, `workflow_evaluator`가 단순 FAIL 여부가 아니라 실패 사유의 정확성까지 채점하게 한다.
- `max_concurrency=1`로 Task 실행 순서를 예측 가능하게 고정해, LangSmith Experiment 결과와 로컬 디버깅 결과가 어긋나지 않게 한다.

# fixed Experiment로 baseline과 비교 (06_compare_experiments.py)

같은 Dataset(`workflow-v1`)에 대해 이번엔 `fixed_target`으로 Experiment를 추가 실행해, LangSmith UI에서 baseline과 fixed 두 Experiment의 Score를 나란히 비교할 수 있게 함.

```python
baselines = experinment_names(client, BASELINE_EXPERIMENT_PREFIX)
if not baselines:
    raise SystemExit("baseline Experiment가 없습니다.")

fixed_experiments = experinment_names(client, FIXED_EXPERIMENT_PREFIX)
if fixed_experiments:
    print("이미 fixed Experiment가 있습니다.")
else:
    client.evaluate(
        fixed_target,
        data=DATASET_NAME,
        evaluators=[workflow_evaluator],
        experiment_prefix=FIXED_EXPERIMENT_PREFIX,
        max_concurrency=1,
        metadata={"version": "fixed", "lesson": "fix-test-evaluation"}
    )
```

- baseline Experiment가 아직 없으면(`05_dataset_evaluation.py --evaluate-baseline`을 먼저 실행하지 않았으면) 곧바로 `SystemExit`으로 중단해, 비교 대상 없이 fixed만 실행되는 상황을 막는다.
- fixed Experiment도 이미 존재하면 재실행 대신 기존 이름 목록만 출력해, `05_dataset_evaluation.py`의 중복 방지 패턴을 동일하게 따른다.
- 같은 `DATASET_NAME`과 같은 `workflow_evaluator`를 baseline·fixed 양쪽에 재사용하므로, LangSmith Experiment 비교 화면에서 `destination` Task 유무 하나가 `workflow_requirement_match` Score 차이로 그대로 드러난다.

# 전체 흐름 정리

1. `.env`의 `LANGSMITH_API_KEY`/`LANGSMITH_TRACING`/`LANGSMITH_PROJECT`를 값 형식까지 검사하는 `langsmith_setting_errors`를 모든 스크립트가 공통으로 재사용해, 잘못된 설정으로 조용히 업로드가 실패하는 상황을 막는다.
2. D_11_Workflow의 `execute_*` Task 함수를 고치지 않고 `@traceable(run_type="tool")`로 감싼 `traced_*` 함수로 교체하기만 하면, 같은 Plan-Execute-Validate 로직이 LangSmith Trace Tree로 그대로 드러난다.
3. `tracing_context(enabled=True)`로 감싼 구간에서 `run_workflow`(`run_type="chain"`)를 호출하면 LLM Planner 사용 여부(`--llm`)와 무관하게 전체 실행이 하나의 최상위 Run으로 묶여 기록된다.
4. baseline Plan은 `destination` Task 누락으로 Validator FAIL을, `runtime_error` Plan은 `compose` Task 누락으로 `execute_plan`의 `ValueError`를 각각 재현해, Validator 실패와 실행 중 예외라는 서로 다른 실패 유형이 Trace에 어떻게 남는지 비교할 수 있다.
5. `WORKFLOW_VERSION` 리터럴 하나만 바꿔 baseline/fixed를 전환하는 방식은, Plan 한 곳만 고쳐도 Validator 결과가 바뀌는 것을 최소 변경으로 보여주는 디버깅 습관이다.
6. `EVALUATION_CASES`를 LangSmith Dataset으로 등록한 뒤 `client.evaluate`로 baseline과 fixed Target을 각각 Experiment로 실행하면, 같은 Evaluator(`workflow_requirement_match`) 기준으로 두 버전의 Score를 LangSmith UI에서 직접 비교할 수 있다.

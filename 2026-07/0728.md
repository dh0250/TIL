# Spring Boot와 FastAPI의 HTTP 기반 서비스 연동 (D_08_fastapi/D_09_spring_integration)

FastAPI는 파일 저장을 담당하고 Spring Boot는 클라이언트 요청을 받아 FastAPI로 전달하는 브리지 역할을 수행. 서로 다른 언어와 프로세스의 애플리케이션을 함수 호출이 아닌 HTTP·JSON 계약으로 연결.

```text
브라우저
  └─ POST /api/files
       └─ Spring Boot :8080
            └─ POST /api/v1/files
                 └─ FastAPI :8002
                      └─ 파일 본문 + JSON 메타데이터 저장
```

- FastAPI는 8002번 포트, Spring Boot는 8080번 포트에서 각각 독립적으로 실행된다.
- Spring의 `application.yaml`에 `fastapi.url`을 두어 하위 서비스 주소를 코드와 분리한다.
- Spring이 외부 요청과 오류 처리를 담당하고, FastAPI는 파일 검증과 저장이라는 역할에 집중한다.
- URL과 요청·응답 스키마를 유지하면 한쪽의 내부 구현이 바뀌어도 다른 서비스에 미치는 영향을 줄일 수 있다.

# FastAPI 파일 업로드 검증과 메타데이터 저장 (fastapi/main.py)

`UploadFile`과 `Form`으로 multipart 요청을 받고 파일의 Content-Type·확장자·크기를 검증한 뒤 UUID 기반 이름으로 저장.

```python
@app.post("/api/v1/files", response_model=FileInfo, status_code=201)
async def upload_file(
    file: Annotated[UploadFile, File()],
    description: Annotated[str, Form(min_length=1, max_length=100)]
) -> FileInfo:
    content_type = file.content_type or "application/octet-stream"
    suffix = ALLOWED_TYPES.get(content_type)
    original_name = Path(file.filename or "").name

    if suffix is None or Path(original_name).suffix.lower() != suffix:
        raise HTTPException(
            status_code=415,
            detail="확장자와 형식이 일치하는 txt/pdf만 허용합니다."
        )

    content = await file.read(MAX_FILE_SIZE + 1)
    if len(content) > MAX_FILE_SIZE:
        raise HTTPException(status_code=413, detail="파일은 1MB 이하여야 합니다.")
```

- 허용 형식은 `text/plain`과 `application/pdf`이며, Content-Type과 파일 확장자가 모두 일치해야 한다.
- 제한보다 1바이트 더 읽어 실제 파일이 1MB를 초과하는지 판별하고, 초과하면 413을 반환한다.
- `Path(file.filename).name`으로 클라이언트가 전달한 경로 부분을 제거한다.
- 실제 저장 이름은 UUID로 만들어 파일명 충돌과 임의 경로 사용을 방지한다.
- 파일과 같은 UUID의 JSON에 원본명·Content-Type·크기·설명·저장명을 기록한다.
- `metadata_path()`는 입력 ID를 `UUID`로 변환해 검증하므로 잘못된 문자열을 파일 경로로 사용할 수 없다.

# RestClient로 multipart 요청 전달하기 (FastApiFileClient.java)

Spring의 `RestClient`로 FastAPI 상태를 확인하고, 브라우저에서 받은 `MultipartFile`을 다시 multipart 요청으로 구성해 전달.

```java
public FileInfo upload(MultipartFile file, String description) throws IOException {
    ByteArrayResource resource = new ByteArrayResource(file.getBytes()) {
        @Override
        public String getFilename() {
            return file.getOriginalFilename();
        }
    };

    HttpHeaders fileHeaders = new HttpHeaders();
    fileHeaders.setContentType(
            file.getContentType() == null
                    ? MediaType.APPLICATION_OCTET_STREAM
                    : MediaType.parseMediaType(file.getContentType())
    );

    MultiValueMap<String, Object> body = new LinkedMultiValueMap<>();
    body.add("file", new HttpEntity<>(resource, fileHeaders));
    body.add("description", description);

    return restClient.post()
            .uri("/api/v1/files")
            .contentType(MediaType.MULTIPART_FORM_DATA)
            .body(body)
            .retrieve()
            .body(FileInfo.class);
}
```

- `ByteArrayResource`의 `getFilename()`을 재정의해야 multipart 파일 파트에 원본 파일명이 포함된다.
- 파일 파트에는 별도 `HttpHeaders`를 붙여 원래 Content-Type을 FastAPI까지 전달한다.
- `MultiValueMap`에 `file`과 `description`을 넣어 FastAPI 엔드포인트의 파라미터 이름과 맞춘다.
- `@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class)`로 Python의 `snake_case` JSON과 Java record의 `camelCase`를 매핑한다.
- Python 함수를 Java에서 직접 실행하지 않고 HTTP 클라이언트로 호출하므로 두 서비스의 실행 환경과 배포를 독립적으로 관리할 수 있다.

# 브리지 컨트롤러의 상태 코드와 오류 변환 (FileBridgeController.java)

Spring 컨트롤러는 FastAPI의 정상 응답과 검증 오류를 전달하고, 연결 실패는 클라이언트가 이해할 수 있는 게이트웨이 오류로 변환.

```java
@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<?> upload(
        @RequestPart("file") MultipartFile file,
        @RequestParam("description") String description
) {
    try {
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(fastApiFileClient.upload(file, description));
    } catch (RestClientResponseException e) {
        return ResponseEntity.status(e.getStatusCode())
                .body(Map.of(
                        "code", "FASTAPI_REJECTED",
                        "message", e.getResponseBodyAsString()
                ));
    } catch (IOException | RestClientException e) {
        return ResponseEntity.status(HttpStatus.BAD_GATEWAY)
                .body(Map.of(
                        "code", "UPLOAD_FAILED",
                        "message", "파일 전달에 실패했습니다."
                ));
    }
}
```

- FastAPI가 4xx·5xx로 응답하면 `RestClientResponseException`에서 상태 코드와 응답 본문을 확인할 수 있다.
- 파일 읽기나 네트워크 통신 자체가 실패하면 502(Bad Gateway)를 반환해 하위 서비스 전달 실패임을 표현한다.
- 상태 확인 중 FastAPI에 연결하지 못하면 503(Service Unavailable)과 `FASTAPI_UNAVAILABLE` 코드를 반환한다.
- `@CrossOrigin`으로 개발 중 사용하는 `localhost:3000`, `localhost:5173`의 브라우저 요청을 허용한다.
- Spring에도 multipart 크기 제한을 설정해 지나치게 큰 요청이 FastAPI로 전달되기 전에 차단되도록 한다.

# LangChain의 Chain과 LangGraph의 Graph 비교 (01_chain_vs_graph.py)

동일한 검색·답변 생성 작업을 LCEL Chain과 LangGraph로 각각 구현해 실행 구조의 차이를 확인.

```python
def build_langchain():
    return (
        RunnableLambda(retrieve_chain_step)
        | RunnableLambda(generate_chain_step)
    )

def build_graph():
    builder = StateGraph(LessonState)
    builder.add_node("retrieve", retrieve)
    builder.add_node("generate", generate)
    builder.add_edge(START, "retrieve")
    builder.add_edge("retrieve", "generate")
    builder.add_edge("generate", END)
    return builder.compile()
```

- LangChain의 `|` 연산자는 앞 단계의 출력을 다음 단계로 보내는 고정 실행 순서를 간결하게 표현한다.
- LangGraph는 처리 단계를 Node로 등록하고 Edge로 실행 순서를 명시한다.
- 단순한 직선형 파이프라인은 Chain만으로 충분하지만, 분기·반복·중단·공유 State가 필요하면 Graph가 적합하다.
- 두 구현 모두 `retrieve → generate`를 실행하므로 같은 입력과 로직에서는 같은 결과를 만들 수 있다.

# State·Node·Edge의 역할 (02_state_node_edge.py)

여행 인원과 입장료로 총액을 계산하는 그래프를 통해 LangGraph의 세 가지 기본 요소를 구분.

```python
class TripState(TypedDict):
    place: str
    travelers: int
    ticket_price: int
    total_price: int
    message: str
    path: list[str]

builder.add_edge(START, "calculate_total")
builder.add_edge("calculate_total", "make_message")
builder.add_edge("make_message", END)
```

- State는 모든 Node가 공유하는 작업 데이터의 형태를 정의한다.
- Node는 일반 Python 함수이며 State를 읽고 변경할 필드만 `dict`로 반환한다.
- Edge는 `START → calculate_total → make_message → END`처럼 실행 순서를 표현한다.
- 앞 Node가 만든 `total_price`를 다음 Node가 읽어 최종 안내 문장을 완성한다.
- `path`를 State에 기록하면 실제로 어떤 Node가 실행됐는지 추적할 수 있어 디버깅에 유용하다.

# Reducer로 State 업데이트 누적하기 (03_state_reducer.py)

여러 Node가 같은 `notes` 필드를 반환할 때 기존 값을 덮어쓰지 않고 조사 결과를 차례로 누적.

```python
class ResearchState(TypedDict):
    topic: str
    notes: Annotated[list[str], operator.add]
```

- 기본 State 업데이트는 같은 필드의 이전 값을 새 값으로 덮어쓴다.
- `Annotated[list[str], operator.add]`는 기존 리스트와 새 리스트를 더하는 Reducer 규칙을 지정한다.
- 각 조사 Node는 자신이 만든 메모 하나만 반환해도 장소·예산·식사·교통 결과가 모두 보존된다.
- Reducer는 병렬 작업이나 여러 단계가 하나의 State 필드에 결과를 모을 때 특히 중요하다.

# Conditional Edge로 질문별 경로 선택 (04_conditional_routing.py)

질문을 먼저 분류하고 예산·장소·일반 질문에 따라 필요한 Node만 실행.

```python
def choose_route(
    state: RouterState
) -> Literal["budget", "destination", "general"]:
    return state["route"]

builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", choose_route)
```

- `classify` Node가 질문의 키워드를 검사해 `route`를 State에 기록한다.
- Conditional Edge는 라우팅 함수의 반환값과 같은 이름의 Node로 이동한다.
- 모든 질문에 같은 작업을 실행하지 않으므로 불필요한 처리와 비용을 줄일 수 있다.
- 복합 의도에서는 분류 조건의 순서가 결과에 영향을 준다. 예산 키워드를 먼저 검사하므로 “입장료가 싼 실내 장소”는 예산 경로로 이동한다.
- 어느 조건에도 해당하지 않는 질문은 `general` 경로로 보내 안전한 기본 동작을 제공한다.

# RAG 과정을 Graph로 분리하기 (05_rag_graph.py)

문서 검색과 LLM 답변 생성을 각각 Node로 나눠 RAG의 검색 결과와 최종 답변을 State에서 따로 확인.

```python
class RagState(TypedDict):
    question: str
    context: list[str]
    answer: str
    path: list[str]

builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "generate")
builder.add_edge("generate", END)
```

- 문서를 `OpenAIEmbeddings`로 벡터화해 `InMemoryVectorStore`에 저장한다.
- `retrieve` Node는 질문과 유사한 문서 두 개를 검색해 `context`에 넣는다.
- `generate` Node는 검색된 문서만 근거로 답하도록 프롬프트를 구성한다.
- 검색 결과와 생성 결과가 별도 State 필드에 남아 오답이 Retrieval 문제인지 Generation 문제인지 구분하기 쉽다.
- 수업 데이터에 근거가 없는 질문은 억지로 답하지 않고 모른다고 답하도록 지시한다.

# Query Routing으로 RAG와 일반 답변 선택 (06_question_router.py)

여행지 문서가 필요한 질문만 VectorStore 검색을 수행하고, 일반 여행 질문은 LLM으로 바로 전달.

```text
START → classify
          ├─ rag     → retrieve → rag_answer → END
          └─ general → general              → END
```

- `classify`는 장소명·입장료·실내·무료 등의 키워드가 있으면 `rag`, 아니면 `general`로 분류한다.
- RAG Branch는 `retrieve → rag_answer`를 실행해 내부 문서를 근거로 답한다.
- General Branch는 검색 없이 일반 모델 답변을 생성하므로 불필요한 Embedding 검색 비용을 쓰지 않는다.
- `context`와 `path`를 함께 출력하면 어떤 경로가 선택됐고 검색이 실제 수행됐는지 확인할 수 있다.
- 라우터 정확도가 전체 답변 품질과 비용에 직접 영향을 주므로 실제 서비스에서는 단순 키워드 외에 분류 모델이나 구조화 출력을 사용할 수 있다.

# 전체 흐름 정리

1. FastAPI는 업로드 파일의 형식·확장자·크기를 검증하고 UUID 이름과 JSON 메타데이터로 저장한다.
2. Spring Boot는 `RestClient`로 FastAPI 상태를 확인하고 multipart 파일 요청을 전달한다.
3. 브리지 컨트롤러는 FastAPI의 검증 오류와 연결 실패를 적절한 HTTP 상태와 에러 코드로 변환한다.
4. LangChain은 고정된 직선형 작업을 간결하게 연결하고, LangGraph는 State·Node·Edge로 실행 흐름을 명시한다.
5. Reducer를 사용하면 여러 Node의 State 업데이트를 덮어쓰지 않고 누적할 수 있다.
6. Conditional Edge는 질문 의도에 맞는 Branch만 선택해 불필요한 작업을 줄인다.
7. RAG를 Retrieval과 Generation Node로 분리하면 검색 근거와 답변 생성 과정을 각각 관찰할 수 있다.
8. Query Router는 내부 문서가 필요한 질문만 RAG로 보내 답변의 근거성과 처리 비용을 함께 관리한다.

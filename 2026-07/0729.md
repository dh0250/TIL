Workflow와 Agent의 실행 주체 차이를 비교하고, 모델에게 전달되는 Tool 계약(이름·설명·입력 Schema)의 구조를 확인. 실제 `create_agent`가 만드는 HumanMessage·AIMessage·ToolMessage 흐름을 추적한 뒤, LangGraph로 직접 구성한 ReAct Graph에서 Tool 실패 후 재검색으로 회복하는 과정과 Checkpointer 기반의 Thread별 대화 기억까지 실습.

# Workflow와 Agent의 실행 주체 비교 (01_workflow_vs_agent.py)

같은 여행 질문을 개발자가 작성한 if문 Workflow와 실제 OpenAI 모델이 판단하는 Agent에 각각 전달해 Tool 선택 주체의 차이를 비교.

```python
def run_workflow(question:str) -> workflowResult:
    needs_destination = any(word in question for word in ("장소", "실내", "관광지"))
    needs_budget = any(
        word in question for word in ("비용", "예산", "얼마", "입장료", "계산")
    )

    path: list[str] = []
    if needs_destination:
        path.append("search_destination")
    if needs_budget:
        path.append("estimate_day_budget")
    path.append("write_answer")
    ...

agent = create_agent(
    model=model,
    tools=[search_destination, estimate_day_budget],
    system_prompt="너는 여행 도우미다. 필요한 경우에만 Tool을 사용한다. ..."
)
```

- Workflow는 질문에 특정 키워드가 있는지를 개발자가 미리 정한 규칙으로 검사해 실행할 Tool과 순서를 고정한다.
- Agent는 같은 Tool을 모델에게 제공하고, 질문과 Tool Schema를 보고 실제 호출 여부와 순서를 모델이 결정한다.
- Tool이 필요 없는 인사말 질문에서는 두 방식 모두 Tool을 호출하지 않아야 정상이다.
- 복합 요청(장소+예산)에서 Workflow는 두 조건을 모두 검사해 순서대로 실행하지만, Agent는 모델이 두 Tool을 모두 호출할지 스스로 판단해야 하므로 결과가 달라질 수 있다.
- `extract_tool_calls`로 Agent 메시지에서 모델이 실제로 만든 `tool_calls`만 뽑아 Workflow의 고정 경로와 나란히 비교한다.

# Tool 계약: 이름 · 설명 · 입력 Schema (02_tool_contract.py)

일반 Python 함수는 실행할 수 있지만 모델이 사용법을 알 수 없다는 점에서 출발해, `@tool`과 `args_schema`가 함수에 이름·설명·입력 Schema를 붙여 모델에게 제공하는 계약임을 확인.

```python
class BudgetInput(BaseModel):
    """estimate day budget tool이 받을 입력"""
    travelers: int = Field(description="여행 인원수")
    ticket_price: int = Field(description="1인 기준 입장료(원)")
    meal_budget: int = Field(description="1인 기준 식비(원)")

@tool(args_schema=BudgetInput)
def estimate_day_budget(travelers: int, ticket_price: int, meal_budget: int) -> int:
    """인원수와 1인 비용을 사용해 여행자의 하루 전체 예산을 계산"""
    return calculate_day_budget(travelers, ticket_price, meal_budget)
```

- 일반 함수에는 `args_schema` 속성이 없지만 `@tool`로 감싼 객체에는 있어, 모델에게 전달할 JSON Schema가 함수 자체와 별개로 존재함을 보여준다.
- Schema 검증(필수 필드 누락, 타입 불일치)은 함수가 실행되기 전에 Pydantic `ValidationError`로 걸러진다.
- 업무 규칙 검증(인원 0명, 음수 금액)은 Schema를 통과한 뒤 함수 내부의 `ValueError`로 처리되는, 서로 다른 층의 오류다.
- `search_destination`처럼 조건에 맞는 결과가 없을 때 반환하는 "검색 결과 없음"은 입력 오류가 아니라 정상적으로 실행된 결과이므로 예외를 던지지 않는다.
- `selected_tool.args_schema.model_json_schema()`로 모델에게 실제로 전달되는 입력 Schema를 그대로 출력해 확인할 수 있다.

# 실제 Tool Calling 메시지 추적하기 (03_create_agent.py)

`--run` 옵션으로 실제 OpenAI 모델을 호출해 HumanMessage → AIMessage(Action) → ToolMessage(Observation) → AIMessage(Final Answer)로 이어지는 메시지 흐름을 하나씩 해석.

```python
def print_message_trace(messages: list) -> None:
    for index, message in enumerate(messages, start=1):
        if isinstance(message, HumanMessage):
            print(f"{index}. HumanMessage - 사용자 질문")
        elif isinstance(message, ToolMessage):
            print(f"{index}. ToolMessage - Observation")
            print("     Tool 이름: ", message.name)
        elif isinstance(message, AIMessage) and message.tool_calls:
            print(f"{index}. AIMessage - Action")
        elif isinstance(message, AIMessage):
            print(f"{index}. AIMessage - Final Answer")
```

- 같은 Tool 계약(장소 검색, 예산 계산)을 실제 모델에 제공해 `DEMO_CASES` 네 가지 질문에서 모델이 어떤 Tool을 몇 번 호출하는지 관찰한다.
- `AIMessage.tool_calls`가 있으면 Action, `ToolMessage`는 그 Action의 Observation, `tool_calls`가 없는 `AIMessage`는 Final Answer로 구분된다.
- `tool_call_id`로 Action과 Observation이 하나의 호출로 짝지어져 있음을 메시지 구조에서 직접 확인할 수 있다.
- `compare_expected_tools`는 호출 순서가 아니라 필요한 Tool 집합이 모두 사용됐는지를 비교하며, 같은 Tool이 중복 호출되면 별도로 관찰 로그를 남긴다.
- Tool이 필요 없는 질문에서는 `tool_calls`가 비어 있는 AIMessage 하나만 생성되는지가 PASS 기준이 된다.

# ReAct Graph: Action-Observation 반복과 실패 회복 (04_react_graph.py)

`create_agent`가 감춰둔 Tool 호출 반복을 LangGraph로 직접 구성해, 검색이 실패했을 때 모델이 검색 조건을 바꿔 재시도하는 과정을 그래프 State에서 관찰.

```python
builder = StateGraph(MessagesState)
builder.add_node("agent", call_model)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "agent")
# tools_condition: 마지막 AIMessage에 tool_calls가 있으면 tools로, 없으면 END로
builder.add_conditional_edges("agent", tools_condition)
# ToolMessage를 포함한 전체 State를 모델이 다시 읽어 다음 행동을 결정
builder.add_edge("tools", "agent")
```

- `destination_lookup` Tool은 첫 호출에서 `search_mode="strict"`로 정확히 일치하는 결과가 없으면 `NOT_FOUND`와 함께 `retry_hint`를 반환한다.
- 시스템 프롬프트 규칙에 따라 모델은 `NOT_FOUND` Observation을 읽고 핵심 조건 하나로 `search_mode="broad"`를 다시 호출해야 한다.
- `agent ↔ tools` Edge가 순환 구조를 만들어 Action(Tool 호출) → Observation(Tool 결과) → 다시 Action을 판단하는 반복이 가능해진다.
- `analyze_recovery`는 검색 mode가 `["strict", "broad"]` 순서로 바뀌었는지, `NOT_FOUND`와 `FOUND` Observation이 모두 있었는지를 검증한다.
- 예산 계산에 필요한 정보(인원·입장료·식비)가 부족한 질문에서는 값을 추측해 Tool을 호출하지 않고 사용자에게 되묻는지를 `analyze_clarification`으로 확인한다.

# Checkpointer로 Thread별 대화 기억 유지 (05_agent_memory.py)

`InMemorySaver`를 Checkpointer로 연결해 같은 `thread_id`의 이전 메시지에서 이름·동행인·예산을 기억하고, 다른 `thread_id`에는 그 정보가 전혀 없음을 대조.

```python
agent = create_agent(
    model=ChatOpenAI(model="gpt-4o-mini", temperature=0),
    tools=[recommend_destination],
    checkpointer=InMemorySaver(),
    system_prompt=(
        "2. 현재 Thread의 대화에서 가장 최근 이름, 동행인, 전체 예산을 찾는다.\n"
        "3. 세 정보가 모두 있을 때만 Tool을 호출한다.\n"
        "5. 사용자가 정보를 수정하면 가장 최근 값을 사용한다."
    )
)
```

- `thread_config(thread_id)`로 만든 `{"configurable": {"thread_id": ...}}`가 Checkpointer가 대화를 구분하는 단위가 된다.
- "이름은 수진이고 아이와 여행해, 예산은 20만원"처럼 정보만 전달하는 Turn에서는 아직 추천 요청이 아니므로 Tool을 호출하지 않아야 한다(`verify_no_tool`).
- 이후 "내 조건에 맞는 장소를 추천해줘"라는 짧은 질문만으로도 Agent가 같은 Thread의 이전 메시지에서 이름·동행인·예산을 찾아 `recommend_destination` 인자를 채운다.
- 예산을 15만원으로 수정한 뒤에는 가장 최근 값이 Tool 인자에 반영되는지를 확인해, State가 단순 누적이 아니라 최신값 우선임을 보여준다.
- 다른 `thread_id`(student-2)에는 같은 Checkpointer를 쓰더라도 이전 대화가 전혀 없으므로, Agent는 정보를 추측하지 않고 다시 질문한다.

# 전체 흐름 정리

1. Workflow는 개발자가 정한 규칙으로 Tool 실행 여부와 순서를 고정하고, Agent는 같은 Tool을 두고 모델이 스스로 호출 여부를 판단한다.
2. Tool은 함수에 이름·설명·입력 Schema를 붙인 계약이며, Schema 검증(필수 필드·타입)과 업무 규칙 검증(함수 내부 로직)은 서로 다른 층에서 처리된다.
3. 실제 Tool Calling은 HumanMessage → AIMessage(Action) → ToolMessage(Observation) → AIMessage(Final Answer) 순서의 메시지로 관찰할 수 있다.
4. LangGraph의 `agent ↔ tools` 순환 Edge는 Tool 실패 후에도 모델이 Observation을 읽고 조건을 바꿔 재시도하는 ReAct 패턴을 가능하게 한다.
5. 정보가 부족한 요청에서는 값을 추측해 Tool을 호출하지 않고 사용자에게 되묻는 것이 안전한 기본 동작이다.
6. Checkpointer는 `thread_id` 단위로 대화를 저장해, 같은 Thread에서는 이전 정보를 Tool 인자로 재사용하고 다른 Thread에는 정보를 노출하지 않는다.
7. State에 최신값을 반영하도록 지시하면 사용자가 정보를 수정했을 때 Agent가 옛 값이 아닌 최근 값으로 Tool을 호출한다.
